## 1. 业务背景与衡量指标

### 1.1 背景、目标与证据

已有管理底座及单文件游戏样例，尚无已验收的玩家商店、交易权益和独立接入闭环。项目建设独立游戏商店与通用接入平台，以故事互动切入；优先检验线索探索/推理玩家假设，用户已明确以业务功能设计推进，不要求市场研究、用户访谈或真实运营数据作为前提。

平台负责发现、身份、商品订单、可信支付与权益、接入运营及约定数据；游戏独立负责剧情、页面、玩法和专有数据。浏览器案例用于理解交互，不照搬 UI，不强制统一剧情引擎或框架。固定品牌和 Logo 保留。

`已确认` O1 运营协助供给；C1 三类计费分版；S1 声明支持的最小平台存档；M1 商店响应式网页；P1 未来平台商店小程序；T0 Steam 用途待定；GUEST-01 游客直接试玩，进入付费购买流程时登录；U1 访问权不按重进消耗；B1 买断按明确范围。

`已确认` V0.1 单案例 G-A 买断，V0.2 增加 G-B/章节，V0.3 场景及首期回归。V0.1 交付目标为 E2 公开真实付费，不以 UI Demo、本地运行、测试替身或支付沙箱代替。后续测试和发布仍需获批。

`已确认` 首发方向中国，提供方就是我们自己；平台完成后完整设计开发 G-A、G-B 两类原创游戏并真实对接。当前不要求商业证明、市场访谈或真实运营数据，优先完成平台业务设计。完整游戏已纳入总体交付范围，但当前不提前开始游戏详细设计或开发。平台内部完成不等于包含完整游戏接入的商业闭环已经交付。

`已确认 LG1 / PK2 / OP1` 邮箱密码、邮箱验证及邮件找回；章节/场景升级买断需要差价；普通停售停新售并保留已购游玩，安全暂停另处置。UP1 合格历史实付净额、X1 六组补缺及 FN1 金额汇总已确认纳入草案；GP1 游客兼容进度确认导入、EV1 购买/完整免费领取/私人云档前验证、RF1 人工审核默认仅撤本次升级已确认；SS1单继续档/上一恢复点、AD1人工注销最后确认、RS1分类人工受理、LC1简中/CNY已确认；FS1字段/统计、DP1分类保留和SV1售后/服务政策已实际确认，见[当前有效决策](../../03-架构/决策/当前有效决策.md)。

`已确认 PG1` 首发必须承接同账号、同游戏、兼容试玩进度；原试玩 HTML 作为起点保留，未来完整游戏不能只剩一段验证脚本。游戏的剧情、谜题及页面仍由独立游戏工程负责。

## 2. 用户故事与状态流转机

### 2.1 角色、信息与核心路径

访客浏览发现并直接试玩；玩家管理自己的游玩、订单、权益与存档；本项目团队作为提供方，在平台完成后用独立工程交付完整游戏/版本和范围说明；运营协助审核、发布、查单和处理问题；游戏只访问本作品与当前上下文被授权的数据。后台管理账号不自动等于玩家账号，现有权限底座需适配验证。

信息架构包含商店、搜索/筛选、游戏详情、登录、购买/订单结果、我的游戏、订单/售后及账户；管理端包含作品/版本/审核、商品/范围、订单/权益/售后、必要运行记录和权限留痕。独立游戏是明确的运行边界，不是统一商店剧情页面。详见配套线框。

主路径：发现 → 详情/兼容/内容提示 → 游客或已登录试玩 → 到付费边界明确购买范围 → 登录/注册（如需要）→ 返回原游戏和商品 → 下单/支付 → 核验付款 → 交付权益 → 启动独立游戏 → 保存/返回 → 再进入。免费或已有权益可跳过新订单；不支持试玩/存档时明确说明。

### 2.3 核心业务规则与权限

- `已确认 GUEST-01` 游客试玩免登录，进入付费购买流程前登录；支付、权益归属及账号切换不得只依据游戏传入数据。
- `已确认` U1 重复进入不再消耗；授权有效且作品可用时可重玩。停售与服务变更按OP1/SV1，不新增默认有效期，不添加次数账本。
- `已确认` B1 保留购买时承诺范围；未来新增内容另作说明，不将修复更新作为再次收费依据。历史范围变更须可追溯。
- `已确认 PK2/UP1/RF1` 需要差价升级；已有权益完整覆盖不重复购买，部分覆盖说明可抵范围与应补价。抵扣基准 UP1 已定，来源实付减确认退款、只抵一次且不超买断价，零补款记升级不伪造支付。退款联动遵循 RF1，普通售后按SV1，见 [账号/存档/售后规则](账号进度与退款规则-V1.0-提交稿.md)。
- `已确认 R-02 / PG1` 首发必须承接同账号、同游戏且兼容的试玩进度；转换失败保留原档并提示恢复。购买本身不篡改剧情进度。
- `已确认 OP1 / R-03` 普通停售停止新交易，保留有效已购访问与适用运行版本；安全故障可暂停启动并说明，恢复/永久结束服务按SV1，不能删除交易或存档证据。
- `已确认 RS1/SV1` 售后入口可查单并提交理由；受理不等于批准退款。退款处理目标和RF1退款联动已定；普通售后见POL-11/12，不写“数字商品一律不退”或无依据的时限。
- `本轮提交的权限职责` 管理操作按作品、交易支持、发布和权限职责授权；查单只展示必要信息，游戏不能查询其他作品玩家数据或平台凭据。

账号身份/验证/生命周期的动作权限、GP1 导入可跳过及冲突处理、RF1 现金/权益分开与原单联动，详见 [规则 V0.3](账号进度与退款规则-V1.0-提交稿.md)。SS1 存档槽位、AD1 注销流程、RS1 普通售后及 LC1 简中/CNY已确认；FS1/DP1/SV1完整规格与政策已确认；实现及适用性仍须在后续阶段验证。

已取消/已撤升级/已撤销/已注销/已导入是该次业务的结果，不阻止后续合法的新业务。删除账号后仍需保留的记录不因状态终结而公开或重新激活。重新开始进度先确认，只影响明示的当前作品/范围，失败保留原可用进度；具体槽位与兼容仍依游戏声明。

新增事件的 action_type 表达 register/verify/reset/delete 业务动作；精确枚举与载荷在架构确认。M-09 以订单/付款/退款/费用核对记录为准，不仅凭分析事件累加。M-03 对零补款另列升级交付，不混入付费订单完整率分母；本机试玩保存与私人云档结果分别统计。

同次操作的成功/失败不同时作为最终结果；后续恢复用可关联的新结果，不改写历史。保存/恢复结果附对应 `operation_ref`，发布结果附 `release_attempt_ref`；付款与交付用订单/付款关联，启动结果用 `run_ref`。事件格式、去重和缺参数处理在正式接口规范中明确。

指标取数：M-01 使用详情与试玩就绪事件，同一可证浏览会话关联；M-02 使用订单及可信付款记录，按订单去重而非点击次数；M-03 使用可信实收、应交付范围和实际权益记录，不只依赖消息到达；M-04 使用启动获准与相应就绪结果；M-05 使用有效请求及相应确认结果；M-06 使用访问拒绝、运行/存档失败及独立隔离验证记录；M-07 使用发布发起和实际生效记录；M-08 使用有效售后、可信实收/退款及处理记录。未决结果单列，统计截点/观察窗口按FS1，人工处理目标按SV1；已确认去重/窗口/截点详见字段与统计稿，不能以成功事件数除以成功加失败掩盖未完成操作。

不采集密码、令牌、完整对白、全部线索、完整玩家输入或完整存档作为分析参数。必要诊断与运营证据受权限和保留规则控制；具体去重、可信度和跨端关联在架构设计。不把事件总线收到一条消息当成真实付款。
