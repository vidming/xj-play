# 独立游戏接入案例与验收关注清单

- 版本：V0.1
- 日期：2026-10-24（Asia/Shanghai）
- 状态：用户接入要求已明确；案例拆解、验证安排与业务规则是待评审候选，尚未实施。
- 当前角色：产品专家，整理后续架构与实现必须回答的问题。
- 依据：[当前有效决策](../../03-架构/决策/当前有效决策.md)、最初任务书、[本地源码核查](../sources/独立前端游戏源码核查-20261024.md)、[小红书观察](../sources/小红书鬼媒婆案例观察-20261023.md)。
- 边界：本文件不规定技术栈、运行容器、接口字段、数据库结构、SDK 或部署方式。

## 1. 必须保持的理解

需要建设的是通用游戏商店与接入平台。游戏有自己的程序、页面、剧情结构和状态，平台提供通用的身份、商品、权益、启动和数据能力。接入后保持两者职责清楚，不把游戏逻辑搬进商店代码。

“独立开发前端游戏”与“接入平台后调用平台服务”可以同时成立。需要分别证明：

| 层次 | 需要证明什么 | 不能用什么替代 |
| --- | --- | --- |
| 玩法可实现 | 独立游戏能自行推进剧情、探索页面、处理选择与状态 | 商店页内置一段试玩文本 |
| 接入可运行 | 从平台进入独立游戏，保持身份与明确的授权范围，并能返回平台 | 一个无法关联身份、权益的外链 |
| 商业闭环可信 | 订单、支付结果和授予的权益可以核对，未授权内容受到相应保护 | 浏览器中设置“已购买”或禁用按钮 |
| 数据关联明确 | 平台可关联用户、作品、运行版本、游玩会话、权益及约定事件/存档 | 根据剧情文本猜测用户进度 |
| 交付真实 | 已批准测试环境中实际运行并保留验证证据 | UI Demo 的模拟登录、模拟支付或图片 |

## 2. 两类案例

| 案例 | 游戏自行负责 | 平台需要验证的通用能力 | 现有证据及限制 |
| --- | --- | --- | --- |
| G-A：故事主线与选择分支 | 对话、文本、选项、角色状态、分支、结局、专有存档结构 | 独立启动、试玩边界、章节/场景权益、买断、返回和继续 | 《第七位来电者》有前端故事、推进与本地保存代码；尚未运行接入验证 |
| G-B：线索、链接与仿真网页探索 | 虚构论坛、报刊/档案检索、页面路由、线索状态与推理规则 | 多页面/路由过程中维持接入关系，受限内容的访问、重新进入、返回平台和约定数据交互 | 小红书作者笔记及截图展示报刊检索、资料目录；未取得源码、未运行游戏、未验证底层路由或存档 |

G-B 可以是独立单页程序，也可以由多个前端页面组成；这些只是待比较形式，不在产品阶段选定。截图中的“虚构网站”不能被误读为平台必须访问现实网站或抓取真实个人资料。

后续可用原创最小案例表达 G-B 的交互结构，不默认复制“鬼媒婆”的作品资产。G-A 是否直接适配现有样例，也需在实施计划中确认范围。两个案例都不能被强制改成同一套剧情格式或商店页面模板。

## 3. 独立前端可行性与信任边界

本地 G-A 代码已经给出剧情推进、选择和本地存储由前端完成的例证。对 G-B，目前只能判断其可见交互属于浏览器可以表达的页面、输入与导航模式，不能据截图声称该作品本身是纯前端、单文件或不依赖服务端。

若游戏依赖实时生成、多人共享状态、外部私有服务或必须保密的规则，需要另外评估游戏侧服务；不承诺全部故事游戏都能仅靠静态资源完成。

需要在架构阶段重点回答：

- 哪些内容可以随试玩资源公开分发，哪些付费内容必须在可信授权后才能取得。
- 如果完整付费文本和资源已随前端包下发，隐藏按钮、改 URL 或混淆脚本不能构成可靠的内容访问保护；已经合法下发给浏览器的内容也不能被承诺绝对防复制。
- 游戏侧报告“已完成场景”“已选择选项”等事件，不等于支付已成功，也不能自行授予购买权益。
- 本地进度可以影响游戏体验；购买与授权依据不能来自可编辑的本地存档。
- 平台知道“玩家有权进入哪个商业内容范围”，无需理解该范围内每一句剧情或每一个线索。

以上是必须论证的风险与边界，不是已批准的资源分包、鉴权或加密方案。外部资料核查见 [可信边界来源](../sources/独立前端游戏能力与可信边界核查-20261024.md)。

## 4. 不依赖剧情结构的商业映射

以下是业务含义示意，不是接口、字段表或已选数据模型。

| 模式 | 玩家购买的对象 | 与游戏侧内容的关系 | 不应推导出的规则 |
| --- | --- | --- | --- |
| 场景付费 | 一项明确说明范围的场景访问权益 | 游戏提供自己的内容标识，可映射一个或一组页面、节点或资源 | 一个网页链接必然等于一个收费场景；每次点击都要收费 |
| 章节付费 | 一章或一个内容包的访问权益 | 由游戏说明哪些内部内容属于该购买范围，是否有前置内容另行定义 | 所有游戏都必须有章节；平台重写游戏剧情树 |
| 买断 | 约定版本/内容范围的完整访问权益 | 覆盖范围、后续新增内容与版本兼容需明确 | 自动包含未来一切 DLC、永久托管或所有渠道版本 |
| 试玩/免费 | 明确的可体验范围或免费完整作品 | 可采用独立试玩版本或同游戏内的试玩范围，架构阶段比较 | “免费试玩”必然包含全部内容；试玩进度一定能迁移 |

需要后续细化的规则包括：同一作品是否允许多种模式共存、已购章节再买断如何计价、重复购买如何处理、分支内容如何覆盖、退款/撤销如何影响访问、游戏下架后已购访问如何处理。当前不自行决定折扣、退款承诺或永久访问政策。

## 5. 必须追溯的数据关系

| 关系 ID | 需要关联的业务信息 | 游戏与平台的责任界线 |
| --- | --- | --- |
| REL-01 | 平台账号与一次游戏启动/游玩会话 | 平台确认身份；游戏接收约定范围内的身份信息，不接管平台账号凭据 |
| REL-02 | 游戏、实际运行版本与接入能力 | 平台知道启动了哪个版本；游戏说明兼容范围，不因更新默认沿用全部旧能力 |
| REL-03 | 商品、订单、支付结果与授予权益 | 平台维护可信交易关系；游戏不能用点击、事件或本地标志替代 |
| REL-04 | 权益与游戏侧场景/章节/完整作品范围 | 游戏定义内部内容标识；平台维护约定的商业访问关系，不保存完整剧情树作为前提 |
| REL-05 | 试玩范围、正式访问与进度转移 | 平台说明当前进入模式；游戏解释进度是否可继承，不能默默丢失或夸大迁移能力 |
| REL-06 | 账号、游戏、存档版本与恢复记录 | 是否提供平台存档待选；游戏解释专有数据与兼容，不能把本地保存称为跨设备云存档 |
| REL-07 | 用户/会话、作品版本与约定行为事件 | 平台收取必要事件；不默认采集完整对白、所有输入或敏感个人信息 |
| REL-08 | 失败反馈、受影响版本与处理结果 | 区分启动/支付/授权/保存/游戏内部问题，便于玩家返回与运营定位 |

本表定义关联需求，不提前规定主键、表结构、载荷格式、传输令牌或统计平台。
