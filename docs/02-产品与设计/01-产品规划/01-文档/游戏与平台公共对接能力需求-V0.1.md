## 1. 不随接入形式改变的业务要求

游戏在自己的程序中运行玩法，仍需要与平台进行约定的数据交互。资源托管位置和页面是否嵌入不能替代这种关系。公共能力不等于强制所有游戏启用所有功能，也不等于全部经同一种传输机制提供。

平台定义通用业务语义和访问边界，游戏声明自己支持的能力并负责适配。界面可由不同网页/未来客户端承载，平台不能依赖某个网页按钮才能维护订单与权益。跨渠道是否共享账号与购买权另行确定。

## 2. 公共能力覆盖表

| 编号 | 公共能力与双方职责 | 可验收业务结果与必要异常 | 追溯 |
| --- | --- | --- | --- |
| CAP-01 | 身份与游玩上下文：平台核实当前身份/游戏/版本/进入模式，游戏在被允许的范围使用 | 能核对归属；访客、登录失效、账号切换与过期启动有明确处理；不向游戏暴露平台账号凭据 | REL-01/02；INT-02/10/12 |
| CAP-02 | 作品与能力声明：提供方说明版本、设备、试玩、存档和兼容要求，运营审核发布 | 平台按实际能力展示，无法运行时说明原因；不能把声明支持当作已测试 | REL-02；INT-01/11/16 |
| CAP-03 | 启动、恢复和返回：平台决定可启动范围，游戏保留路由与游戏内页面 | 可以进入、退出、重进；链接/路由、刷新和前进后退不丢失约定关系；失败可返回 | REL-01/02/08；INT-02/08/12 |
| CAP-04 | 商业范围与权益查询/校验：游戏定义内容标识，平台维护与商品及权益的关系 | 区分试玩、免费、已购及不可访问；查询结果、版本和有效期变化可处理；不采信本地解锁标记 | REL-03/04/05；INT-03/06/07/13 |
| CAP-05 | 购买意图与结果恢复：游戏提出所需购买范围，平台管理下单、支付事实和权益 | 可以在平台明确商品/价格并回到游戏；取消、失败、待确认、重复操作与迟到结果可查；游戏事件不自行授予权益 | REL-03/04/08；INT-04/05/09/16 |
| CAP-06 | 最小存档交互：平台维护账号/游戏归属与约定版本信息，游戏解释自己的数据 | 声明支持的游戏能保存/读取/恢复；隔离账号和游戏；冲突、不兼容、失败与不支持清楚反馈；不是平台统一剧情格式 | REL-06；INT-10/11/14/15 |
| CAP-07 | 必要事件交互：游戏报告约定事件，平台维护归属及必要关联 | 启动/结束、进入模式、版本、错误和必要转化可追溯；断网、重复、顺序与重试在架构明确；不默认上传全部线索、对白或输入 | REL-07/08；INT-14/16 |
| CAP-08 | 接入兼容与生命周期：双方声明支持范围，运营控制作品/版本发布状态 | 升级、回退、停用和下架对启动、已有权益和存档的影响有规则；游戏崩溃不被误认支付失败 | REL-02/06/08；INT-11/12/13/16 |

不是每一次启动都必须创建付费订单，不是每条事件都应计费，也不是每个游戏都应上传存档。支持哪些能力、缺失时如何呈现，以及哪些是接入底线，应在 PRD 与架构中分别明确。

## 3. 两类案例中的观察点

| 能力 | G-A 故事选择 | G-B 仿真网页探索 |
| --- | --- | --- |
| 身份/进入模式 | 进入故事前识别试玩或正式范围 | 多页面/路由和重新访问维持或恢复约定上下文 |
| 内容权益 | 游戏自有章节或场景标识对应商品范围 | 游戏自有调查区域、档案包等标识可映射商品，不把每条 URL 自动当收费单位 |
| 购买/返回 | 触及边界后明确购买项，购买结果核对后继续 | 从不同虚构页面发起购买并回到正确上下文，不能凭 URL 参数自解锁 |
| 存档 | 保存游戏自有分支/状态数据 | 保存游戏自有线索/调查状态；平台无需理解每条线索 |
| 事件/异常 | 识别启动、版本、退出和必要失败 | 识别导航/刷新导致的恢复问题；必要统计不自动扩展为完整浏览轨迹采集 |

表格是产品推演，不证明参考游戏当前具备这些对接能力。

## 4. 逐版拆分原则

最早的真实接入 MVP 就需要 CAP-01/03/04/05 的最小链路，以及用于定位作品版本的 CAP-02、声明支持的 CAP-06、最小 CAP-07 和必要 CAP-08。不能以“以后做 SDK”为由只放外链或写死用户。

后续版本增加商业映射、第二类案例和兼容/异常的覆盖深度。第一版不需要完整开发者门户、全量事件平台、自动分账或所有游戏的跨设备能力。精确组合见 MVP 候选（历史材料已清理），尚未批准。

## 5. 后续产物契约

| 阶段 | 对本清单的继续工作 |
| --- | --- |
| PRD | 补能力启用条件、权限、状态、玩家可见反馈、数据最小化及逐项验收；不把框架选型当业务规则 |
| UI/UX | 设计试玩边界、购买返回、登录失效、保存失败/不支持等状态；按端呈现，不照搬案例 UI |
| 架构 | 统一身份/权益/内容访问的信任边界；比较接入方式；设计认证授权、最小信息传递、错误码、幂等、重试、回调、分页、超时、版本及生命周期规范；必要时交付 SDK/适配器 |
| 计划 | 逐小版本把 CAP、REL、INT 对应到任务、环境、用例与责任；不预先假定真实团队人数 |
| 开发/测试 | 用独立游戏实际调用并验证成功、失败、隔离与恢复，保留端到端证据 |
| 部署 | 在获批环境重新验证；测试替身、沙箱与生产支付分开记录 |

本阶段未设计或实现上述接口。所有 INT 项仍未执行。
