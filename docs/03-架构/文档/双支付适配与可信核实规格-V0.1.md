# 双支付适配与可信核实规格

V0.1；2026-10-26（Asia/Shanghai）；阶段3架构草案；未实现、未接真实商户、未验收。

依据：[当前有效决策](../决策/当前有效决策.md)、[官方协议核查](../资料/支付宝与微信官方协议核查-20261025.md)、[物理字典](物理数据字典与迁移草案-V0.1.md)、[OpenAPI](../资料/平台OpenAPI-V0.1.json)。下文官方事实的来源编号对应核查报告，其他事务与状态规则属于项目设计。

## 1. 双渠道与终端

支付宝、微信都属于首期，研究先后不缩减范围。网页终端覆盖具体采用哪些收银产品仍受产品资格与终端确认约束；缺资格时记录交付阻塞，不用模拟支付代称已上线。

| 环境 | 支付宝 | 微信 | 不可省略的条件 |
| --- | --- | --- | --- |
| PC网页 | PAGE：电脑网站支付 | NATIVE：电脑展示二维码，手机扫码 | 应用/商户/经营类目及产品资格；不是同手机长按二维码方案 |
| 手机外部浏览器 | WAP：手机网站支付 | H5：从已配置域名跳转 | H5单独资格、域名和移动环境；客户端回跳不是到账 |
| 微信内置浏览器 | 引导打开系统浏览器承接原订单 | 引导打开系统浏览器承接原订单，再按H5资格发起 | PT1已确认；重新核身份及订单归属；JSAPI不进首期 |

来源：A01/A02/A05–A10/A18、W01–W10/W21/W24/W26。PT1已于2026-10-26实际确认：首期覆盖PC网页与手机外部浏览器双支付；微信内仍可浏览，两渠道支付均引导系统浏览器。JSAPI、公众号身份关联和小程序不进入首期。跨浏览器链接只用于定位原订单，不能作为身份凭证；外部浏览器重新登录并由服务端核订单归属、有效期和当前支付状态，复用原订单，不因外跳新建订单，也不携带用户令牌或购买结论。

首期机器契约与PT1一致：`PaymentCreate`、`PaymentAttempt`和渠道动作只接受PAGE/WAP/NATIVE/H5，JSAPI请求按参数错误拒绝；未来若启用公众号网页支付，须发布新版本契约并另行确认APPID、OpenID、授权目录、商户绑定与测试条件。

## 2. 适配器边界

同一Java应用内的逻辑接口：`createAttempt`、`queryPayment`、`closeAttempt`、`verifyNotification`、`submitRefund`、`queryRefund`、`normalizeCashEvidence`。平台交易模块决定业务；适配器只解释渠道协议，不直接修改游戏权益或存档。

| 统一值 | 支付宝映射 | 微信映射 |
| --- | --- | --- |
| paymentAttemptId | 服务器生成满足渠道规则的out_trade_no | 独立的out_trade_no；不复用支付宝编号 |
| 现金来源唯一键 | channel＋merchantRef＋trade_no | channel＋merchantRef＋transaction_id |
| 退款稳定号 | 原交易＋out_request_no | out_refund_no |
| 支付金额 | CNY分经十进制定点转换为元字符串，禁浮点 | total分整数＋currency |
| 支付核实 | 验签通知/查单的trade_status及完整匹配 | 验签解密通知/查单的trade_state及完整匹配 |
| 退款核实 | refund_status等实际业务状态；查询成功码不足以证明成功 | 查询status/通知refund_status；PROCESSING不是成功 |
| 通知成功应答 | 纯文本success | 204无正文；不套平台code/msg/data |

来源：A05–A16、W07–W20/W28–W33。统一模型不抹平签名原文、字段单位、状态含义和应答差异。

支付宝采用当前官方推荐的RSA2能力，具体公钥/证书模式由商户材料确定；原始通知参数按渠道规则验签，不把JSON序列化规则套到表单。微信APIv3区分商户请求私钥、微信支付公钥/平台证书及APIv3解密密钥；按标识选择受信验签材料，不能对未知serial自动信任。原始请求体、时间戳、nonce在验签前保持原字节，验签通过后按协议解密。密钥轮换期间保留受控的必要旧信任材料；不打印密钥、完整通知或用户凭据。来源：A15/A16/A21、W12–W16/W28/W29。

## 3. 同订单跨渠道状态机

`order`表达购买承诺，`payment_attempt`表达每次渠道动作，`cash_fact`记录每笔实际收款，`grant`表达履约来源。它们不共用一个“成功”字段。

1. 对有效、正应付订单，短事务锁订单修订，登记CREATING尝试及稳定渠道号，然后释放锁再请求渠道。超时置UNKNOWN并查原号，不能自动换号。
2. 收银页/二维码生成后置WAITING。玩家刷新或网络重试复用同一尝试；页面回调只触发平台查询。
3. 用户切换渠道时，先锁订单与活跃尝试修订，标记旧尝试关闭请求；在事务外查单、必要时关单，再回事务核实。若已成功，进入交付；若关闭被可信确认，才允许新渠道尝试；UNKNOWN保持“查证中”并提供支持出口。
4. 该策略降低双付概率，但不能假设跨渠道关单/到账绝对原子。晚到账始终记录真实cash_fact，哪怕本地订单已取消/关闭或账号已进入注销。
5. 正常匹配且尚无主履约来源时，选择PRIMARY并登记交付任务。另一笔实收记DUPLICATE，金额不符记AMOUNT_MISMATCH；都保留真实金额/币种/核实证据，进入售后核对，不再发第二份权益。
6. 同一渠道号重复通知与主动查单汇合到同一现金唯一键，效果幂等；通知ID去重不能替代现金唯一键。

不在数据库事务内等待渠道网络；关单成功只说明适用渠道尝试，不代表抹除先前现金。支付宝TRADE_CLOSED可能包含已付款后全额退款，必须结合历史现金核实，不能统一映射为“从未收款”。来源：A09–A14、W17/W18/W30/W33；跨渠道守卫属于项目设计。

## 4. 通知可靠接收与补偿

- 通知入口独立于Cookie、CSRF和管理员认证，使用渠道验签、重放控制及商户/应用/单号/金额/币种/事件类型核对。Webhook不因用户登出而失效。
- 微信按官方5秒内应答要求设计；先可靠落盘受控收件和待处理引用，再应答。若无法在时限内完成匹配核实，可可靠保存已验签原始信封进入受限队列，核实前不授予权益。未可靠落盘不回成功。
- 有效签名但无匹配本地订单的通知进入UNMATCHED人工查证，不能随意生成“正常订单”。来源合法不等于业务可直接交付。
- 可信现金落库、订单核实修订和交付outbox在同一事务；交付任务按来源唯一关系重入。任务失败展示“已收款、交付处理中”，不要求再次支付。
- 补偿覆盖CREATING/UNKNOWN、在途关单、未发权、退款UNKNOWN、撤权异常。每任务有lease、退避、下次核对及人工接手记录；具体频率/吞吐在资源与测试阶段固定。
- 短时间戳窗口、nonce去重不能挡住渠道合法重试；受控信封保留与重试按官方规则区分旧签名重放和真实重投。未知时间偏差告警且查单，不自动免验签。

来源：A09/A10、W13/W16/W19/W20；可靠收件与outbox是本平台设计。通知密文或原文保留期限、加密与访问必须单独登记，不能混进普通30日行为日志。

## 5. 退款与权益

在同账号/作品守卫下检查原现金：`已确认退款＋在途预留＋本次金额≤实际实收`，同一退款号重复执行复用原金额与来源。提交渠道后UNKNOWN保持额度预留，先查原号；退款受理不能显示已到账。支付宝退款查询至少间隔官方要求的时间；具体调度结合限流确定。来源：A13/A14、W19/W31–W33。

售后批准方案明确cashFactId、应退额、受影响授予/升级及不受影响来源。现金核实与撤权结果分别记录；现金已退而撤权失败时，不倒改现金状态，受影响范围进入查证并补偿。

RF1仅撤升级：正补款只退此次新增实际收款；零补款没有现金可退。撤此次买断来源并释放对应抵扣，原仍有效章节/场景来源保留。不按退款金额比例猜测剧情范围，不一次性撤销其他有效来源。重复付款退款逐笔原路处理，不将两渠道金额合成一笔跨渠道退还。

## 6. 账号注销、报表和对账

最终确认注销立刻撤会话，不阻断可靠收件。晚到账仍归原主体墓碑与原订单，转受控支持处理，不恢复旧账号，不转移给同邮箱新主体。

现金按可信发生时刻归期，verifiedAt用于迟到修订；退款、重复收款、未知费用、在途退款分列。金额核对以现金/退款/费用事实为依据；游戏或Web观察事件不作账本。渠道账单获取能力和实际权限仍待查证，不能声称已完成自动对账。

## 7. 待验证与后续验收用例

尚未进行任何真实支付或退款。后续获准实施后，至少验证：通知重投与查询并发、关单超时、渠道切换与晚到账、同单两笔实收、金额/商户不符、收款后交付崩溃、退款受理后超时、已退现金撤权失败、RF1零补款、注销后晚到账。每例区分替身/沙箱/真实环境，不以接口文档存在代替测试。
