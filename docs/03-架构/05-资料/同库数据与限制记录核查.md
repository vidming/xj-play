# 同库数据与限制记录核查

更新：2026-10-26，Asia/Shanghai。阶段3架构核查；数据库元数据为实际只读结果，模型与协议为设计，未建表、未迁移、未运行验收。

## 1. 当前决定与适用范围

用户直接要求平台及后续每个独立游戏的所有表、表数据先放在当前MySQL MCP连接的数据库，以业务前缀区分。本次记为SD2，覆盖LR1独立限制数据库及CD1另选数据库的前提。直接消息即为依据，不再要求用户重复确认合库；完整架构、具体资源及生产部署仍未验收。

同库只改变数据部署归属。游戏仍可独立工程、自选前端框架、自有剧情和专有数据；平台负责身份、现金、权益及可信访问。OSF1私有对象方向继续有效，游戏包、图片、受限内容及存档对象正文不因“表与表数据同库”自动改存MySQL。限制日志对象CAS继续禁用。

当前规格以[恢复规格第7节](../03-文档/部署资源与恢复规格.md#7-同库限制记录事务与恢复边界)、[当前有效决策](../01-决策/当前有效决策.md)和[物理字典](../03-文档/物理数据字典与迁移草案-V0.1.md)为准。本文原位替代旧独立限制方案报告，不保留两份当前拓扑。

## 3. 平台与游戏表的归属

| 对象 | 当前约定 | 权限及生命周期 |
| --- | --- | --- |
| 平台业务 | `xj_`，按目录、交易、运行、存档、运营、限制等领域组织 | 由平台迁移和可信服务管理；游戏不得直写现金/权益/限制 |
| 既有管理底座 | `system_`、`infra_`等源码固定前缀 | 复用前逐项确认导入与迁移，当前未导入 |
| 每个独立游戏 | 登记`xjg_<gameKey>_`，例`xjg_ga_`、`xjg_gb_` | 自有剧情、线索、角色和玩法表；仅授权本游戏明确表清单 |

`gameKey`为小写字母开头的字母数字、最长16位；`xj_game.data_namespace`可空且唯一，登记后不可复用。具体表名由受控迁移定义，不能把HTTP参数、URL、contentKey拼成SQL标识。前缀只是归属，不是权限隔离、测试环境或独立故障域。

纯前端游戏可以通过SDK/API使用通用身份、权益、存档和事件，不必每个游戏新增后端。需要专有持久逻辑时，由可信游戏服务操作其最小授权表，并经平台接口核身份及访问范围。浏览器不持数据库凭据；同库不等于游戏可以查询平台账号凭据或其他游戏数据。

独立游戏服务通过HTTP调用平台仍有各自提交边界，不能因连接同库就声称自动原子。以原业务ID、幂等、outbox/回执及查证协调，不在数据库持锁期间等待游戏HTTP、支付渠道或对象存储。

删除覆盖平台及所有关联游戏私人数据，按游戏适配器与最小清理范围核回执。单游戏升级/恢复不能整库覆盖其他游戏、付款事实或最新限制；先在隔离暂存区核当前身份、删除覆盖和revision，再受控合入。

## 4. 同库限制事务及模型变化

当前同源模型为48表、533列、77条逻辑关联、物理外键0条，全部属于`xj_play`，全部关联在同库。独立游戏具体玩法表尚未设计或创建，不计入48表。

用户随后明确RK1：关联从语义上可理解即可，不建立真正外键以降低维护成本。模型`references`、`REF`及ER虚线只表示逻辑目标和基数，`physicalForeignKeys`为空；不生成FOREIGN KEY或ON DELETE/UPDATE约束。保留主键、必要唯一键和查询索引，应用写入事务核目标存在/状态/作品及主体归属，关联写入和删除共用守卫；导入、修复、批处理及孤儿巡检遵循相同规则。

保留门禁、操作、重放、头、事件、检查点6张限制/恢复设计表。删除仅为旧双库协议设置的`xj_rl_operation`镜像模型，统一引用`xj_restriction_operation`。固定锁序为门禁→头→原操作→业务守卫→目标行，业务限制、操作结果、APPLIED事件、头及必要outbox在同一InnoDB连接和短事务提交。

失败显式回滚整事务，不保留独立PREPARED/ABORTED补写协议。COMMIT响应未明属于请求UNKNOWN，原键查当前可信写端；同键同计划返回原成功结果，不先用旧revision拒掉原成功重试。同键异计划拒绝，不能换键制造第二次操作。旧备份缺行不能证明该请求没有执行，更不能据此重发现金动作。

确定编码与检查点承接完整原回执，规范见恢复规格7.4。4 MiB包长下须在写前限制计划、事件和快照及封装；超限停止压缩，保留唯一事件载体，不能截断或默默提高实例配置。

## 5. 共享恢复边界与当前缺口

同库使业务和限制能够同事务提交，也使平台、每个游戏、限制链、检查点、幂等记录与outbox一起遭受整库回滚。哈希链与自洽旧快照`1..H`不能证明事故前不存在`H+k`，恢复出的OPEN也不能自授权开放。

当前`log_bin=OFF`，不具备本实例binlog路线的PITR前提。[S3] 周期快照是否存在以及能否覆盖最后接受的限制未知，不能宣称恢复安全或RPO15分钟/RTO4小时达标。目标继续保留，不自动降低，也不自动启用binlog、重启或恢复LR1。

恢复时先在库外关闭业务入口、任务和新支付，实际隔离旧写端及旧连接；核可信最后接受范围与完整可恢复计划，先形成删除排除/未决隔离，再核有效对象。缺证的私人恢复、付费资源及相关范围继续隔离；公开目录分范围只读不代表整体恢复完成。备份材料在库外保存不等于新增应用数据库，也不表示备份已验证。

### 9.3 一致逻辑全量、DDL与权限条件

1. **一致性只覆盖满足条件的事务表。**官方手册说明`--single-transaction`使用REPEATABLE READ事务读取一致状态；5.7.14固定tag的`start_transaction()`在第5280—5310行实际设置该隔离级别并请求一致快照。该tag第504—513行明确只保证支持多版本的引擎，列举InnoDB；MyISAM/MEMORY等不能因此获得相同保证。由此不能把“默认InnoDB”当作全部实际导出表、系统表和账号材料都已处于一致快照。[P5][P9]
2. **允许业务DML继续不等于允许并发DDL。**5.7.14 tag的选项说明明确警告并发ALTER、DROP、RENAME、TRUNCATE破坏快照隔离；5.7手册另外列出CREATE。后续备份设计应协调结构变更窗口，不以事务快照替代DDL管控，也不声称这些DDL在5.7.14的具体失败表现都已实测。[P5][P9]
3. **同一恢复集合须有同一快照边界。**平台、游戏、限制链、幂等和outbox若靠逻辑全量保持事务对应，必须进入经核定的一致导出范围；分别启动的多个事务快照不能自动拼成同一时点。该项为由快照语义对本项目同库事务的推导，尚未选择工具或执行导出。[P9]
4. **权限随导出对象和选项变化。**手册列出被导出表的SELECT、视图的SHOW VIEW、触发器的TRIGGER，以及未用单事务选项时的LOCK TABLES等条件；不能复制一个高权工具账号来代替备份权限设计。5.7.31起的特定PROCESS要求不套到5.7.14，也不能因此宣称任何备份方式都绝不需要PROCESS或其他权限。[P5]

上述参数名只用于解释官方语义，不是已批准的备份命令或工具选择。固定tag源码是该版本参考实现的静态证据，不证明实际宿主所用客户端版本、导出选项、全部对象范围或恢复速度。

### 9.4 全量、binlog坐标与PITR前提

**一致全量与日志坐标必须对应。**官方5.7手册说明`--master-data`从SHOW MASTER STATUS取得文件名/位置，要求启用binlog并具有RELOAD及足以查询该状态的权限。SHOW MASTER STATUS接受SUPER或REPLICATION CLIENT；不能据此把SUPER认作读取坐标的唯一选择。与单事务选项组合时，导出开始阶段仍会短暂获取全局读锁，不能宣称整个流程完全无锁。[P2][P5][P6]

这不是仅存在于后续版本的描述：5.7.14固定tag的`do_show_master_status()`从第5038行起读取日志状态；`do_flush_tables_read_lock()`在第5217—5233行发起刷新和全局读锁，其注释说明长更新等竞争仍可能导致等待。因此不能把“设计上短暂”写成实际无等待或固定耗时。单独在导出前后任取一个坐标，也不自动证明它对应导出快照。[P9]

官方PITR要求恢复全量后的后续binlog；必须有覆盖目标边界的连续可读日志，并正确衔接全量对应坐标，不能缺一段后仍宣称恢复到最后接受状态。binlog的启用是前提，日志文件的位置、可取得性和保留也必须有证据。[P7][P8]

主代理提供的当前`log_bin=OFF`、`gtid_mode=OFF`、`binlog_format=ROW`仅作已报告前提，本协作者没有复查实例。按官方语义，**当前关闭binlog，不满足依赖持续记录新变更的本实例PITR路线前提**；ROW设置不会替代开启binlog。5.7存在文件名/位置路线，不能把GTID开启当作该路线的必要条件。以后开启也不能补写此前未记录的变更；既往是否另存全量/日志仍未知，本节不推定全部历史恢复材料不存在，不修改参数或触发重启。[P6][P7][P8]

### 9.5 数据库备份与本项目恢复完整性的区别

本项目的同库事务使业务事实与限制在提交时有共同边界；导出旧一致快照仍只能证明快照覆盖的时点，不能证明此后没有接受新的限制或现金操作。全量存在、哈希链自洽或导出完成，均不能单独证明已恢复完整的限制尾部；这个结论是官方快照/PITR语义结合本文第4、5节的架构推导，不冒充MySQL自带的“最后接受范围证明”。[P7][P9]

数据库中保存ObjectRef或对象版本号，不等于备份了私有不可变对象正文；数据库导出也不自动包含宿主/渠道秘密、加密密钥及其受控恢复能力。后续恢复材料必须分别核对数据库与日志边界、精确对象版本及完整性、所需密钥/权限，以及最后接受的限制/未决操作范围；本节不设计新的日志承载、不恢复LR1授权，也不据此新增服务或预算。

**当前缺口：**应用及备份账号的实际授权、备份工具/客户端精确版本和选项、全部表/对象导出范围、DDL协调机制、全量与连续日志及坐标的真实保留、库外对象/密钥和最新限制范围证据、恢复演练结果均未由本轮核实。主代理报告的高权工具账号、默认行格式或日志变量，均不能代替这些验证；不宣称RPO15分钟/RTO4小时达标。
