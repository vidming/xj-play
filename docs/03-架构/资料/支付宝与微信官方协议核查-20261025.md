实际核查日期：**2026-10-25（Asia/Shanghai）**  
阶段：阶段 3，只读官方协议研究。  
适用问题：游戏数字商品通过网页收款时，可研究哪些官方支付产品、协议闭环和接入前置条件。

- 本文提供渠道协议事实、证据索引和待资源条件，不设计数据模型、项目 API、表结构或代码实现。

## 2. 取证方式

1. 已尝试实际 `web.run` 搜索和打开官方页面，本次没有取得可用的返回正文或来源标识，未将其计入证据。
2. 随后使用 Python 标准库 `urllib.request` 直连官方公开资料，只发送读取文档的 GET 请求。主要资料来自 `opendocs.alipay.com`、`pay.weixin.qq.com`，另读取微信官方开发文档与腾讯客服官方说明。未调用支付交易、OAuth、商户管理等真实业务接口。
3. 支付宝旧路径返回 HTTP 200 的网页框架，但未包含目标协议正文。经官方 `llms.txt` 找到新的 `.md` 文档后，才将具体段落计为已核实；微信亦使用官方索引链接的 `.md` 正文。HTTP 200 本身不是读到正文的证明。
4. 下列各来源条目的“日期”都是本次实际读取日期，不是文章发布日期。部分微信页面标注了 2026-10-22 等更新时间；这里只能证明读取时页面呈现了该内容，不能证明商户后台已同步获得权限。
5. “已读正文”表示读取到了与结论有关的产品描述、字段、规则或应答说明；代码示例和图片未全部逐项验证，示例没有执行。仅凭索引或正文中的其他链接，不声称已读被链接页面。
6. 未使用博客、聚合站或第三方教程补齐缺失协议；未安装、升级、开通产品、操作商户后台或发送消息。唯一写入产物为本文。

## 3. 浏览器场景与首期双支付的关系

| 入口环境 | 支付宝对应研究路径 | 微信对应研究路径 | 能确认的边界 |
| --- | --- | --- | --- |
| PC 网页 | 电脑网站支付 `alipay.trade.page.pay` | Native 下单后展示 `code_url` 二维码 | 用户在网页发起；微信由手机微信“扫一扫”付款。支付宝可跳转官方收银台或使用文档支持的页面扫码模式。[A01、A05、W01、W07] |
| 微信外的手机浏览器，如系统浏览器 | 手机网站支付 `alipay.trade.wap.pay` | H5 下单取得 `h5_url`，跳转唤起微信 | 微信 H5 不是在微信内置浏览器中直接支付，且需要安装微信客户端。[A02、A06、W02、W08、W24] |
| 微信内置浏览器打开的网页 | 官方 FAQ 指引转到系统浏览器后进行支付宝手机网站支付 | JSAPI 下单取得 `prepay_id`，使用 `WeixinJSBridge` 调起 | 不能承诺微信内能直接拉起支付宝；微信 H5 不能直接代替 JSAPI。[A18、W03、W09、W10、W24] |
| 微信小程序 | 本次不研究其支付接入 | 单独的小程序支付场景 | 网页 JSAPI 使用微信浏览器桥，小程序是小程序运行环境。即使下单接口或产品权限复用，也不代表终端、APPID、登录方式和调起方式相同。[W03、W09、W10、W25] |

**H5/JSAPI 不等同微信小程序。**H5 是手机外部浏览器网页；JSAPI 是微信内置浏览器网页。网页 JSAPI 需要对应公众号 APPID 下的 `openid`，并符合公众号认证、商户绑定及支付授权目录条件；不能把小程序 `wx.login` 取得的身份直接当作公众号网页用户身份。官方 JSAPI 下单文档将两种 OpenID 获取入口分别列出，并明确 APPID 一致性。[W03、W06、W09、W21、W26]

微信 Native 官方产品正文明确为 PC 网页收款，并说明不支持相册识别或长按识别该支付二维码。因此，**不能把“手机网页展示二维码，用户在同一手机长按”作为已核实的微信移动支付方案**。该结论不扩展为对其他产品二维码能力的判断。[W01]

上述对应关系用于界定技术选型条件，不新增“首期所有终端都必须覆盖”的决策。若主任务要求覆盖 PC、外部手机浏览器和微信内浏览器，则需逐项核实 Native/H5/JSAPI 的权限与交互；若某一产品资源暂不具备，应显式列为资源阻塞，不能静默删掉首期微信或支付宝。

## 4. 账号认证、行业与产品权限

### 4.1 支付宝

电脑网站、手机网站两份产品正文当前均列出企业账号、个人账号、个体工商户入口，并要求可正常访问、展示明确经营内容及完整商品信息的网站，以及 ICP 备案、主体一致性或所需授权材料。不能套用“支付宝网页支付必定只允许企业账号”的旧印象，也不能从个人账号入口反推出本项目游戏业务可由个人账号直接收款。[A01、A02]

官方账号文档分别说明个人实名认证与企业账号认证。企业账号流程涉及主体、法定代表人、经营场景和意愿确认等信息；**账号认证、收付款功能、网页应用上线、具体产品开通是不同核实项**。当前未查看本项目任何支付宝账号、商户或应用状态。[A03、A04、A19、A20]

自研接入准备要求创建网页/移动应用，取得 APPID，配置加签与通知相关参数，并完成应用上线及适用产品开通。文档同时提供公钥和公钥证书两种模式；涉及特定资金支出接口的证书要求需按实际产品规则复核，本文不把所有接口统一认定为必须或无需证书。[A03、A04、A15]

游戏经营资格必须细分。支付宝官方签约资料把“游戏”与“游戏周边服务/交易平台”分列，适用商家和材料条件不同，部分情形还列有特殊资质。手机网站产品介绍也区分游戏相关行业规则。**这些只是准入资料线索，不能确定本项目所属类目，更不能据此确认审批或本项目费率。**本文不提供本项目费用报价。[A02、A17]

### 4.2 微信

Native、JSAPI 产品介绍列出的主体包括个体工商户、企业等；H5 产品介绍列出企业、事业单位、政府机关、社会组织，未将个体工商户列入同一主体范围。该事实来自读取日的官方产品文档，不代表本项目符合任何一项。不能假设“已有某个商户号，就自动具备 H5 权限”。[W01–W06]

Native/H5 的接入准备要求合适的已认证公众平台或开放平台账号、商户号、对应产品权限及 APPID 绑定。网页 JSAPI 产品正文要求已认证服务号或符合条件的政府/媒体公众号；不能用任意 APPID 代替。APPID 绑定、产品权限、认证状态均未在本项目验证。[W04–W06]

H5 需配置与实际跳转网页一致的支付域名，官方材料要求包括备案、经营场景及必要的行业证明。H5 权限指引举例列出运营商授权、游戏版号等特殊材料；域名配置页还对经营性网站的 ICP 许可证作出要求。**这里记录的是渠道页面要求，不据此作法律资质认定，也不声称只完成普通备案就一定足够。**应在未来实际申请前按主体、经营类目和网站事实逐项确认。[W22、W23]

微信官方不支持场景正文明确列有账号租售、游戏外挂，并列举若干高风险游戏情形。因此，“通用游戏数字商品”不是足以判断准入的经营描述。该限制不能泛化为“所有游戏数字商品均禁止”，也不能反向解释为未列出的商品一定获准。[W24、W27]

## 5. 支付宝协议闭环

本节研究的是 `alipay.trade.*` 传统网关接口。支付宝通用文档另提及 V3 OpenAPI；本文没有把两种协议的字段、签名或应答格式混合。

### 5.1 下单与签名

| 项目 | 电脑网站支付 | 手机网站支付 |
| --- | --- | --- |
| 接口 | `alipay.trade.page.pay` | `alipay.trade.wap.pay` |
| 产品码 | `FAST_INSTANT_TRADE_PAY` | `QUICK_WAP_WAY` |
| 接入形式 | 服务端 SDK 生成页面表单或跳转内容，交给浏览器访问支付宝 | 服务端 SDK 生成页面表单或跳转内容，浏览器进入支付宝 App/网页 |
| 主要业务参数 | `out_trade_no`、`total_amount`、`subject`、`product_code` | `out_trade_no`、`total_amount`、`subject`、`product_code` |
| 支付结果入口 | `notify_url`；`return_url` 用于用户返回 | `notify_url`；`return_url` 用于用户返回；另有 `quit_url` |
| 证据 | A05、A07 | A06、A08 |

金额字段为人民币元，采用十进制金额语义。公用请求含 `app_id`、`method`、`charset`、`sign_type`、`sign` 等。通用签名文档说明新建应用仅支持 RSA2，RSA2 对应 SHA256WithRSA，并要求 RSA 密钥至少 2048 位；部分具体 API 页仍列历史 RSA 兼容说明，不应据此为新接入选择 SHA1。[A05、A06、A15]

应用私钥用于签署商户请求；支付宝公钥或相应支付宝公钥证书用于验签。同步 JSON 响应验签与异步通知参数验签的原文构造不同，不能把 JSON 重新序列化后当作原始签名内容。应以官方 SDK 和选定模式的文档为准。[A03、A04、A15、A16]

**支付页面生成成功、浏览器回跳及用户点击完成，都不能直接确认付款。**两份快速接入文档要求以异步通知或主动查单结果为准。手机网站文档还说明部分 iOS 场景不会自动切回浏览器，不能承诺所有设备都有自动回跳。[A07、A08]

### 5.2 异步通知：验签、解密与应答

已核实电脑网站和手机网站支付通知为服务器向 `notify_url` 发出的 POST 参数通知。本文读取的交易通知格式并非微信的 `resource.ciphertext` 信封。[A09、A10]

1. 按官方通知规则取得表单参数，去除 `sign`、`sign_type` 后构造待验签内容，用支付宝公钥或适用证书验签。参数应按协议解码、排序，实际实现须避免框架已解码后再重复 URL 解码。[A09、A10、A16]
2. 验签后还需核对 `out_trade_no`、`total_amount`、`seller_id`/适用卖家标识和 `app_id` 与商户订单及收款主体相符。验签通过不等于可以省略这些业务核对。[A09、A10]
3. 支付成功状态为 `TRADE_SUCCESS` 或按协议解释的 `TRADE_FINISHED`。`WAIT_BUYER_PAY` 不是成功；`TRADE_CLOSED` 既可能是未付款关闭，也可能是付款后全额退款，不能直接当成“从未支付”。[A09–A11]
4. 正确处理或识别已处理的重复通知后，返回严格的小写纯字符串 `success`。额外 HTML、重定向等可能使通知被判失败。非成功应答会触发重试；同一通知重试的 `notify_id` 不变。[A09、A10]

**解密边界：**支付宝接入准备把 OpenAPI 内容加密列为选填，通用加密文档说明的是 `biz_content` 请求/响应内容的 AES 加密，涉及密文响应时先验签再解密。不能把这一点写成“所有支付宝支付通知默认都必须 AES 解密”，也不能移植微信 APIv3 的密钥和 GCM 规则。[A03、A04、A21]

**文档差异必须保留：**电脑网站通知页列出的默认触发项只有 `TRADE_SUCCESS` 为 true；手机网站通知页还列有 `TRADE_FINISHED`、`TRADE_CLOSED` 为 true；关单 API 页又列有关闭通知触发说明。本文无法据公开页面确定本项目最终开通配置，故不承诺关闭、到期、全额退款等事件一定通过同一支付通知抵达，以主动查询核实结果。[A09、A10、A12]

### 5.3 查单、关单、退款和退款查询

| 动作 | 官方接口 | 已读到的有限规则 |
| --- | --- | --- |
| 查单 | `alipay.trade.query` | 以 `out_trade_no` 或 `trade_no` 查询；接口成功还需查看 `trade_status`。未收到支付通知应主动查单。[A09–A11] |
| 关单 | `alipay.trade.close` | 适用于等待买家付款状态。已支付订单不能靠关单退款；文档列有交易不存在、状态不合法等错误。[A07、A12] |
| 退款 | `alipay.trade.refund` | 支持全额与部分退款；使用原交易标识、`refund_amount` 和适用的 `out_request_no`。同一退款重试保留原请求号；部分退款需传该号，不同部分退款使用不同请求号。[A13] |
| 退款查询 | `alipay.trade.fastpay.refund.query` | 使用原交易标识与 `out_request_no`。`code=10000` 仅代表本次查询成功，退款成功需检查 `refund_status=REFUND_SUCCESS`。[A14] |
| 银行卡冲退完成通知 | `alipay.trade.refund.depositback.completed` | 是另一个消息通知，文档列有订阅/应用网关以及 `query_options=deposit_back_info` 等条件，不应假设普通支付通知能完整替代它。[A07、A08、A22] |

退款查询文档要求重试保持退款请求号和金额一致，并建议在退款发起后间隔 10 秒以上再查询。查询时暂未返回退款成功状态，不宜立即换号重退。快速接入说明与产品介绍列有退款有效期；本研究不把公开默认值替代本项目签约约定。[A07、A14]

支付重试同样不能随意换号：电脑网站快速接入说明同一商户侧订单号关联原交易；通知说明要求更换 `out_trade_no` 前先查原单，若已成功不得重复支付，若仍等待付款则先关原单。渠道退款请求号幂等不等于本项目的交付天然幂等。[A07、A09、A10、A13]

## 6. 微信 APIv3 协议闭环

### 6.1 下单与客户端调起

| 产品 | 服务端下单路径 | 返回并交给前端的内容 | 必须区分的条件 |
| --- | --- | --- | --- |
| Native | `POST /v3/pay/transactions/native` | `code_url`，转为二维码展示 | PC 展示，手机微信扫一扫；不把长按识别作为已核实方案。[W01、W07] |
| H5 | `POST /v3/pay/transactions/h5` | `h5_url`，从已配置域名网页跳转 | 需要 `scene_info.payer_client_ip`、`scene_info.h5_info` 等；APIv3 字段名不是旧版 `spbill_create_ip`。[W08] |
| JSAPI | `POST /v3/pay/transactions/jsapi` | `prepay_id`，服务端准备调起签名参数 | 下单前取得对应 APPID 下的 `payer.openid`，前端使用 `WeixinJSBridge`。[W09、W10] |

三者要求 `appid`、`mchid`、商户号下唯一的 `out_trade_no`、商品描述、金额及通知地址等。金额使用币种最小单位的整数，人民币为分。Native/H5 的 APPID 可来自其允许绑定的应用类型，但 JSAPI 网页的具体资格仍须符合产品与公众号文档，不因共享下单字段介绍而放宽。[W04–W09]

H5 的 `h5_url` 和 Native 的 `code_url` 具有各自有效期；链接到期与订单是否已支付、是否已关闭是不同问题。下单页明确 `time_expire` 为支付截止时间，**不等于订单关闭时间**。重新取得支付链接前仍须处理原单状态，不能把二维码消失或链接失效作为渠道关单证据。[W07、W08]

JSAPI 调起字段包含 `appId`、秒级 `timeStamp`、`nonceStr`、`package=prepay_id=...`、`signType=RSA`、`paySign`，调起签名与服务端 API 请求签名属于不同场景。客户端回调 `get_brand_wcpay_request:ok` 仍需后端查单；H5 回跳也应触发查单。[W10、W11]

### 6.2 请求认证与密钥角色

所有微信 APIv3 交易请求使用 HTTPS。请求通过 `Authorization` 携带 `WECHATPAY2-SHA256-RSA2048` 认证信息，包括商户号、商户 API 证书序列号、随机串、时间戳和签名。签名使用商户 API 证书对应私钥；有请求体时，签名原文必须与实际发送的请求体一致。[W12、W28、W29]

必须区分以下资源：

| 资源 | 协议用途 | 当前项目状态 |
| --- | --- | --- |
| 商户 API 证书对应私钥及证书序列号 | 商户请求签名、客户端调起签名所需 | 未核实 |
| 微信支付公钥及公钥 ID | 验证微信支付响应和通知签名；按序列号/ID 找对应信任材料 | 未核实 |
| 微信支付平台证书及序列号 | 存量平台证书方案的验签材料 | 是否采用该方案未核实 |
| APIv3 密钥 | 解密回调 `resource`、适用的平台证书密文 | 未核实 |
| APPID 对应身份及网页授权能力 | JSAPI 网页取得该 APPID 下的用户 OpenID | 未核实 |

2026-10-13 更新的开发参数正文推荐新接入采用微信支付公钥方案，平台证书作为存量方案说明。**“用微信支付公钥验签”不等于无需商户 API 证书私钥，也不等于无需 APIv3 密钥。**本研究只读取使用要求，没有申请、下载或读取本项目真实证书密钥。[W12–W15、W26]

### 6.3 支付和退款通知：验签、解密与应答

Native/H5/JSAPI 支付通知正文给出相同的通用支付回调协议；退款结果另用退款通知协议。两类通知均为 POST JSON，业务资源被加密。[W16、W19]

1. 读取 `Wechatpay-Timestamp`、`Wechatpay-Nonce`、`Wechatpay-Signature`、`Wechatpay-Serial` 和**原始请求体**。按 timestamp、nonce、原始 body 及规定换行构造验签串，以对应微信支付公钥或平台证书进行 SHA256 with RSA 验签。不能先改写 JSON 再验签。[W13、W16]
2. APIv3 密钥用于 `AEAD_AES_256_GCM` 解密。使用 `resource.ciphertext` 的 Base64 解码结果、`resource.nonce` 和 `resource.associated_data`，取得业务 JSON。这里的 nonce 与 HTTP 签名 nonce 是不同字段。[W14、W16、W19]
3. 支付成功通知类型为 `TRANSACTION.SUCCESS`；解密后包含 `mchid`、`appid`、`out_trade_no`、`transaction_id`、`trade_state`、金额等。退款通知类型有 `REFUND.SUCCESS`、`REFUND.CLOSED`、`REFUND.ABNORMAL`；包含退款标识和 `refund_status`，不能把所有退款通知一概当成功。[W16、W19]
4. 官方支付/退款通知正文要求 **5 秒内验签并应答**。接收成功返回 HTTP **200 或 204**，无需应答报文；验签失败返回 4xx/5xx 及失败报文。不能照搬支付宝纯字符串 `success`，也不能照搬微信 APIv2 XML 的应答格式。[W16、W19]
5. 官方建议应答后异步处理业务逻辑，并明确重复通知须能正确重入；已处理的通知继续成功应答。通知可能重试，也可能因网络等原因收不到，因此仍需主动查单。[W16、W19、W20、W30]

**工程推导，非新增渠道协议：**为避免“先应答成功、任务随后丢失”，建议在成功应答前完成验签及可靠接收保障，让后续业务可恢复；后续再解密核验或在时限允许时先完成解密及身份金额核验，交付由可信且匹配的结果驱动。验签失败、解密失败或订单不匹配均不得推进付款交付。本文不规定任务存储结构或数据库方案。

官方会以 `WECHATPAY/SIGNTEST/` 错误签名探测商户是否真正验签，不应针对这一前缀特殊放行。`notify_url` 要求公网可访问的完整 HTTPS 路径，不带参数，不能设置登录态门槛。[W13、W20]

### 6.4 查单、关单、退款和退款查询

| 动作 | 官方协议 | 结果判定与限制 |
| --- | --- | --- |
| 按商户单号查单 | `GET /v3/pay/transactions/out-trade-no/{out_trade_no}`，携带 `mchid` | 以验签后的 `trade_state` 判断；`SUCCESS` 为支付成功。未支付时使用商户订单号查询。[W17] |
| 按微信单号查单 | `GET /v3/pay/transactions/id/{transaction_id}`，携带 `mchid` | 微信单号在支付成功后取得，不适合作为所有未支付订单的唯一查询入口。[W17] |
| 关单 | `POST /v3/pay/transactions/out-trade-no/{out_trade_no}/close`，请求体含 `mchid` | 关闭未支付订单，成功应答 `204 No Content`。用户取消、支付超时均可能触发商户关单处理；不是退款接口。[W18] |
| 退款申请 | `POST /v3/refund/domestic/refunds` | 原交易单号二选一、`out_refund_no`、退款/原单金额及币种等。申请成功只表示受理，应继续确认退款结果。[W31] |
| 退款查询 | `GET /v3/refund/domestic/refunds/{out_refund_no}` | 返回 `status`：`SUCCESS`、`CLOSED`、`PROCESSING`、`ABNORMAL` 等；不能把 HTTP 200 或 `PROCESSING` 当作已退款。[W32] |
| 退款通知 | 退款申请中的 `notify_url` 或适用平台配置 | 解密后的字段叫 `refund_status`，与退款查询的 `status` 不同；退款通知不复用支付成功事件。[W19、W31] |

已分别打开 Native、H5、JSAPI 分类下的查询、关单、退款及退款查询正文，接口路径相同；共用路径不表示前端调起、APPID 身份或授权条件相同。产品内的具体证据 URL 见 W17–W19、W31–W32。

微信退款正文规定以支付成功时间加 365 天计算退款期限，可全额或部分退款；同一商户退款单号多次请求只退款一笔。失败或结果不明确时保留原单原参数，先查退款单是否已受理，再按错误码处理；不要自动换号退款。最终失败或异常需要后续处理，不是把原支付改回未支付。[W31–W33]

对于支付重试，官方支付回调和查单指引要求复用原支付单号，避免重复支付；各下单接口也列有商户订单号重复错误。不能把“订单号唯一”写成“任何重复下单必定直接返回原成功内容”。关单请求超时、查单与付款并发时也不能只凭本地超时认定渠道已关闭，应重新查询确认。[W07–W09、W17、W18、W30；末句为工程推导]

## 7. 幂等与异常语义：交给主任务的约束

以下只归纳行为边界，不设计数据结构。

| 问题 | 支付宝已核实规则 | 微信已核实规则 | 可交给主任务的约束 |
| --- | --- | --- | --- |
| 重复支付请求 | 同号关联原单；换号前先查旧单，未付款则先关旧单。[A07、A09、A10] | 商户号下单号唯一；官方指引要求原单号继续支付，避免重复付款。[W07–W09、W30] | 同一业务付款结果未知时，不能因前端刷新或网络超时直接生成新渠道单。跨渠道切换仍须处理旧渠道未决支付。 |
| 重复/延迟通知 | 过滤重复；相同通知重试 `notify_id` 不变。[A09、A10] | 重入处理，已处理仍成功应答。[W16、W19、W20] | 通知与查单可能同时确认同一笔款；数字商品交付不能发生两次。此为工程约束。 |
| 退款重试 | 同一交易下相同 `out_request_no` 只退一次，重试保留号与金额。[A13、A14] | 相同 `out_refund_no` 多次请求只退一笔，原单原参数重试。[W31、W33] | 结果未知先查，不能把同一次重试变成新的退款。 |
| 支付成功后关单 | 等待付款状态才可关单。[A12] | 未支付订单才走关单。[W18] | 已付款走退款流程；本地取消不抵消已发生的渠道付款。 |
| 成功响应含义 | 查单看 `trade_status`；退款查询看 `refund_status`。[A11、A14] | 支付看 `trade_state`；退款申请受理后看退款最终状态。[W17、W31、W32] | HTTP/API 调用成功、收银台生成、支付成功、退款受理、退款成功应分别解释。 |
| 不同成功应答 | 支付通知纯字符串 `success`。[A09、A10] | APIv3 通知 HTTP 200/204，不要求成功 JSON。[W16、W19] | 渠道通知的应答协议分别适配。 |

工程推导：验签和渠道幂等各自只能解决一部分问题，不能自动保证跨支付宝/微信只收一笔、只交付一次或只退一次。主任务仍需明确付款结果未知、跨渠道切换、关单竞争、补偿查询与数字商品交付失败的行为；本文不代做该数据/API 设计。
