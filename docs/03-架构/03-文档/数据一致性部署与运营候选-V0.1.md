# 数据一致性、部署与运营候选

版本：V0.1；更新：2026-10-26（Asia/Shanghai）；阶段3；状态：设计草案，未运行验证。

方向：[当前有效决策](../01-决策/当前有效决策.md)。产品固定字段与政策：[FS1](../../02-产品与设计/01-产品规划/01-文档/字段与统计规格-V1.0-提交稿.md)、[DP1/SV1](../../02-产品与设计/01-产品规划/01-文档/产品规格与政策-V1.0-提交稿.md)。接入：[协议与链路](游戏接入与可信业务链路候选-V0.1.md)。

## 1. 模块所有权

同一 Java 后端发布单元中的逻辑模块，名称是文档边界，不代表已创建工程。

| 模块 | 拥有对象/接口 | 不接管的内容 |
| --- | --- | --- |
| identity | 玩家、会话、验证/找回、注销；调用既有后台认证/RBAC适配边界 | 管理员不自动成为玩家，不用邮箱合并主体 |
| catalog | 作品、版本、资源manifest、内容key、商品及不可变承诺 | 不存平台统一剧情树，不用内容点击收费 |
| commerce | 报价、订单、支付尝试、可信现金事实、退款/费用、支持工单 | 不信浏览器回跳和游戏事件 |
| entitlements | 授予来源、来源范围、抵扣关系、撤销及访问revision | 不把存档进度当权限 |
| runtime | run、意图、当前版本/隔离与受控资源读取 | 不承担故事或谜题状态 |
| saves | 不透明payload归属、版本、CAS、冲突、恢复/清理 | 不解释人物关系和线索含义 |
| operations | 发布审批、支持工作流、审计、分析、补偿和清理任务 | 不用普通异步日志替代账本 |

模块通过应用接口交互。订单/来源关系属于同库一致性边界；不通过前端串调用拼成事务。管理员平台权限与业务对象权限共同校验，菜单隐藏不代表授权。

首期单平台、运营协助供给不是 SaaS 多租户产品。既有底座的 tenant 机制保留但不向游戏开放租户选择；采用服务端固定平台上下文还是逐表显式映射，在完整数据字典中核对，不能随意关闭底座拦截器。发布、交易支持、资源管理及权限管理分别授予最小权限。

### 1.1 SD2统一库与游戏数据归属

用户已明确平台及未来每个游戏的所有表/表数据先使用当前MySQL MCP数据库xj_play；实际只读版本为5.7.14。平台保留xj_及领域表族，独立游戏登记xjg_<gameKey>_；底座system_/infra_等固定前缀保留。具体游戏剧情/线索/角色表待各游戏阶段设计，当前模型不提前生成这些表。

前缀不是授权。纯前端游戏通过平台SDK/API使用通用能力；可信游戏后端如有需要，仅持本游戏明确表清单的权限，不获得平台订单/权益/会话表读写权。通过可信平台API核验作品域身份、范围及付费状态；游戏浏览器不直连数据库。同库后独立服务的HTTP交互仍须幂等、可靠任务及回执查证，不自动形成一个事务，也不在持锁期间等另一服务。

平台安全变更统一先取得环境门禁，涉及限制事件时再锁头及原操作，然后取得业务守卫；业务限制、操作、事件/头及必要outbox同一事务提交。原独立限制库镜像与双库预备/补写已移除。整库回滚也回滚限制与游戏表，无法凭同库日志自证缺失尾部；未证覆盖不开放受影响私人/付费业务。单游戏恢复不得整库覆盖其他游戏或交易事实。当前log_bin=OFF、备份未验，CR1仍为待验证目标。详细规范见[恢复规格第7节](部署资源与恢复规格.md#7-同库限制记录事务与恢复边界)。

## 2. 逻辑数据模型与约束

以下为后续物理 ER/字典的逻辑对象，不是已建立表。公共平台标识由服务端生成，逻辑长度1–128 ASCII；游戏 contentKey 在作品内按大小写精确匹配，物理排序规则须保证此点。金额均 CNY 分整数，正向业务输入不超过999999；真实异常收款完整保留，不能因超过输入上限丢弃。

| 对象 | 主关联/关键字段 | 必须的唯一/一致性约束 |
| --- | --- | --- |
| Player / Session / IdentityOperation | playerId、独立验证/生命周期、会话代次、动作结果 | 邮箱规范化明确；同邮箱重注册新主体；令牌摘要和动作版本不进普通日志 |
| Game / GameVersion / Resource | gameId、不可变版本、manifest摘要、路径、访问条件 | `(gameId,version)`、版本内标准路径唯一；已发布资源不可原地覆盖 |
| ContentKey / VersionCoverage | 游戏自有key、稳定含义、可用版本 | `(gameId,key)`大小写精确唯一；历史含义及已售承诺不可缩减 |
| ProductRevision / ProductCoverage | type、CNY价格、公开状态、覆盖key、promiseVersion | 每份订单绑定不可变revision及范围快照；清单1–1000去重key |
| AccountGameGuard | playerId、gameId、accessRevision | `(playerId,gameId)`唯一；升级/退款/授予同一串行化入口 |
| Quote / QuoteSource | 目标商品快照、来源净实付、抵扣、应付、expiresAt | 10分钟显示有效期；确认时重核来源revision；不持数据库锁等玩家付款 |
| Order / OrderCoverage | 主体、作品、商品承诺、报价快照、应付、状态revision | 同次确认幂等；覆盖快照不可后改；已付、交付和运行分别表达 |
| PaymentAttempt / CashFact | orderId、渠道/商户、尝试号、渠道交易号、金额/发生/核实时刻 | 渠道/商户/交易号唯一；同一订单可有多次真实现金事实，重复收款单独查退 |
| GrantSource / GrantCoverage | 来源种类、订单/免费/升级、覆盖、状态、revision | 同业务来源只发一次；有效访问取来源覆盖并集，不用单个isPaid |
| UpgradeAllocation | upgradeId、现金来源、抵扣额、保留/生效/释放状态 | 同现金净额不能同时被两份有效升级重复使用；释放可追溯 |
| Refund / RefundAllocation | 原付款、批准方案、渠道退款号、现金结果、权益处置结果 | 累计确认退款+在途保留额不超过该付款可退现金；未知不释放可退额 |
| FeeFact / Adjustment | 原付款/退款关联、费用/调整方向、核实状态 | 未知费用为空且明示未知；不可默认为0 |
| Run / PurchaseIntent | 当前主体、游戏/版本、模式、session代次、intentId、resumeHandle | 每次访问核对归属/状态；RT1要求服务端核验意图后向新run受控交付位置；handle不授权、不回显于库接口 |
| SaveHead / SaveBlob / SaveOperation / SaveConflict | player/game、当前/上一blob、revision、格式、operationId | 单current/previous指针；CAS；同次动作幂等；payload最大1048576字节 |
| SupportCase / DeletionJob / RetentionHold | 处理范围、责任角色、截止/复核时刻、分类结果 | 人工响应不等同回执；法定/争议保留按具体对象登记，不冻结全部数据 |
| Outbox / Idempotency / Audit / Analytics | 业务id、版本、payload摘要、结果、traceId | 业务效果幂等；事件投递允许重复；分析明细和交易保留分别处理 |

后续物理规格补类型、每列、索引、逻辑关联策略、状态枚举和清理约束；本表不冒称完整物理字典或已实现数据库。

## 3. 可信付款与交付

1. 服务端生成报价与订单，验证账号/邮箱、作品、商品状态、范围、币种及当前权益；游戏只提出购买意图。
2. 确认下单时绑定商品与范围快照，获得同一账号/作品守卫，重核报价来源与在途事项；创建订单和必要抵扣保留。提交短事务后才调用渠道，网络等待不持行锁。
3. 回跳仅展示“查询中”。可信通知验签、商户/应用、订单、金额与币种核对；必要时主动查单。具体原始字节验签、证书轮换、重放窗口及应答格式以获选渠道官方文档为准，尚未确定。
4. 通知和主动查询进入同一核实入口，保存去重现金事实；同事务更新订单并插入交付 outbox。摘要/金额不符保存异常并查证，不授予正常权益。
5. 工作任务消费 outbox，以唯一来源授予权益并标记交付；崩溃后可重复执行但效果一次。玩家可见“已收款/交付处理中”，不要求再付款。
6. 后续任务核对未知支付、未完成交付及未送达通知；未知不自动转失败。晚到账仍写真实现金事实并进入纠正处理，不因订单已关而丢通知。

不承诺“消息绝对只送一次”，目标是持久化重试、业务幂等和可查证。Redis丢失不能改变付款/权益事实；无缓存时按数据库核实或明确降级，不从过期缓存放行付费内容。

## 4. UP1 差价与 RF1 退款并发

在统一安全门禁及必要限制头/原操作之后，按固定顺序锁定 `AccountGameGuard → 来源现金/退款记录（id排序）→ 升级/订单/授予`，事务短小，死锁重试复用同一幂等键。具体锁策略与索引需后续真实并发验证。

合格来源须同账号/作品/币种、覆盖完整包含于目标、仍有效、无未明退款及未被其他有效升级抵扣。以独立现金事实去重，不按有重叠的商品范围重复计算同笔钱。抵扣为合格净实付之和与目标价的较小值，应补为目标价减抵扣；零补款生成升级及授予，无渠道付款。

付款期间将选定来源的可抵扣额标为“被本升级保留”，阻止第二份升级或原单退款同时挪用。报价10分钟到期不是渠道付款终态；不能只因本地倒计时就释放仍可能到账的保留。关闭需查清渠道结果；晚到账先保留现金事实，若来源已变化进入联动查证，不自动重复发买断或擅自补扣。

仅撤升级：核实退还该次新增实付后，撤该次买断来源、释放其抵扣关联；原仍有效章节/场景保留。原单参与有效升级时进入关联人工审核，展示受影响升级和范围，给逐项方案；不能原单已退却继续当足额抵扣。部分退款须明确对各来源和访问范围的处置，不按退款金额比例随意删除内容。不使用“退款按钮”自动整组退款或扣补差。

每次退款同时预留可退现金额度；渠道未知保持在途，重复指令先查原请求。确认退款现金事实与撤权任务持久化，权益调整失败明确“现金已退/权限处理中”，安全访问在来源处置未收敛时按受影响范围拒绝或查证，其他无关有效来源保留。现金报表不能倒改为未退。

## 5. 存档原子性与恢复

对象存储先写不可变临时blob并验长度/摘要，再在数据库短事务中核对账号状态、版本、operationId及baseRevision，原子切换current/previous引用并保存操作结果。对象写成而事务失败只形成待清理孤儿，不能假报保存成功；清理前再核引用，避免误删在用文件。

读档返回格式/游戏版本及摘要，由游戏确认可读后才记恢复成功；网络读出不是玩法恢复成功。冲突有独立来源保留引用，阻止后台轮转误删；第三来源拒收留本机。恢复/重开先确认且保留被替换current为恢复点。所有私人存档访问核本人、游戏、声明能力及验证状态。

备份必须包含数据库与它引用的不可变对象清单；只有数据库备份不足以恢复云档。恢复到隔离环境后核对引用/摘要、重放删除/撤会话/撤权记录、主动查证渠道晚到账，再决定是否恢复业务。

## 6. 事件、分析与人工运营

客户端白名单事件只用于行为观察；核实付款、免费授予、退款、交付来自对应服务端业务操作。客户端时间仅作辅助，服务端接收/可信发生时刻单列；GAME事件按可信run与原event_ref去重，WEB和SERVER按下节各自可信作用域区分，乱序不反向驱动订单状态。

统计遵循固定 M-01–11：同一有效业务操作重试不加分母；成功、明确失败、未知/处理中、取消并列；24小时是观察窗口，不是自动失败期限。现金按可信发生期归期，迟到核实形成修订版本；净收可负，抵扣/免费/零补款不当收入，费用未知不填0。默认排除预览/测试，保留区间、截点、口径版本及覆盖缺失。

普通行为明细30日滚动清理，注销按7日分类目标处理；真正匿名汇总建议3年，不能将去标识假称匿名。分析不含邮箱、口令、完整对白、线索轨迹、存档或完整支付通知。必要安全证据单独分类，具体适用期限尚需核准。

售后：受理回执与人工回应分开；48自然小时人工首响、72小时持续更新、7自然日给方案或查证状态、30日未解人工升级，均按已确认SV1。工单记录实际处理角色、到期/超期、下一复核与现金/权益结果；不代表已有客服人员。实施计划再落实真实责任人与接手方式。

### 6.1 事件编号、去重键与可信作用域

HTTP及游戏桥继续使用`event_ref`表示原事件编号，通信重试保持原编号及原载荷。客户端不能指定持久化`event_key`、事件来源、实际环境或主体；服务端从入口和经验证的上下文绑定。来源/作用域不从`fields`中的自报账号、run或view_ref获得。

| 来源 | 服务端绑定的作用域 | 原编号及重试要求 |
| --- | --- | --- |
| GAME | 当前入口经验证的固定run公开ID；其作品、版本、主体与模式由服务端核定 | 同run原event_ref重试为同次观察；不同run即使编号相同仍分别记录 |
| WEB | 平台签发并验证的浏览会话不透明ID＋经校验存在且允许观察的作品ID；不是客户端自报view_ref | 同会话、作品的原event_ref保持稳定；不同会话/作品不互相去重；会话变更后的新观察使用新作用域，旧队列不得换新会话重报；没有可验证原上下文时明确拒绝，不跨账号猜合并 |
| SERVER | 可信生产模块＋持久业务事件的稳定身份 | 从事务/outbox等已持久化业务事件取得event_ref并在重试中复用；不能只用订单ID代替其多次不同事实，更不接受浏览器补报现金成功 |

存储键为`lowerhex(SHA-256("XJAE/KEY/1" || part(environmentRef) || part(purpose) || part(source) || part(scopeRef) || part(event_ref)))`。`part(s)`为4字节无符号大端UTF-8字节长度加原UTF-8字节，不做大小写折叠或隐式Unicode归一化；scopeRef有多个字段时按上表固定顺序分别使用part拼接后再作为scopeRef编码。固定域`XJAE/KEY/1`是键派生协议版本，不随应用发布变化；environmentRef与LIVE/TEST/PREVIEW由服务端绑定，在同一重试生命周期内稳定，不能使用每次请求新生成的requestId、traceId或当前时间。最终event_key为64个小写十六进制字符，列保留128位容量，不截断原编号拼接。

`xj_analytics_event`仅以`event_key`建立业务唯一键，另保留public_id唯一键；不以可空run_id参与唯一键，也不使用跨来源的原event_ref全局去重。并发由唯一键裁决，冲突后查当前可信写端已提交原事件，比较已核来源/作用域下规范化的event_type、原occurred_at及白名单fields：一致返回duplicates；不一致按`IDEMPOTENCY_MISMATCH`拒绝，不覆盖原行、不把更换类型当成新事件，不刷新原received_at/created_at或重复累加指标。禁止覆盖式upsert或静默忽略异载荷冲突。

哈希输入不含载荷，使相同原编号异载荷能被查出。时间先转UTC并按DATETIME(6)微秒精度规范化再存储与比较；大于微秒精度且不能无损表示的值明确拒绝，不由数据库隐式舍入。JSON先拒绝重复键，按Schema类型比较，忽略对象键顺序、保留数组顺序；字符串不隐式归一化，数值按字段约定的精确值比较。received_at、重试次数和当前商品/账号展示信息不混入原载荷，归属核验继续按当前状态执行。批量事件按EventReceipt逐项返回accepted、duplicates或rejected，不因一项冲突把其他项伪报成功。

对外回执accepted/duplicates/rejected仍关联请求的原event_ref，不把内部散列当作客户端重试编号。原编号不能包含正文或凭据；哈希不使观察记录匿名，subject_ref、view_ref及所有关联仍按既有30日明细、注销分类清理处理。删除会话/run等定位载体前先确定分析清理范围，不能只剩无法关联主体的哈希键；SERVER的普通分析副本与必要现金/审计原事实分开清理。

清理后不承诺永久保留分析去重记录，也不以该短期唯一键承担现金或权益防重。迟到受理窗口必须在开放采集前配置并验证，不得超过普通明细保留目的允许的窗口，具体延迟限值仍待收口，不在此擅自修改产品政策。过期/失效会话、run及已注销主体的旧队列明确拒绝，不返回“本次已保存”；服务端重投核原事件生命周期及清理状态，不能把到期分析副本重新生成。恢复先施加删除范围再处理旧队列，不以重投重新计算保留起点。

后续验证须覆盖：两个游戏/两个run同编号均接收、同run同事件仅记一次、同编号异类型或载荷拒绝、无run的WEB多会话互不覆盖、服务端业务事件重投不重复、客户端伪造来源/作用域不能改归属。当前只是统一架构与模型，不是已运行的事件处理器。

## 8. 删除与备份不复活

AD1最终确认后立即使凭据、私人操作和适用run失效；以独立分类任务清理私人资料/云档/冲突来源，7自然日目标；备份残留隔离且30日目标消退。存在具体法定/争议必要性时建立受限hold，90日复核、必要性终止后30日目标清理，适用更短期限优先。

删除日志/墓碑与恢复操作联动，至少覆盖所有仍可能恢复的备份时间窗；其访问、最小字段和清理也要登记。灾备恢复先重放已核实删除与撤权，再开放服务。外部游戏只通知其实际持有的数据并记录回执，不能伪称远程擦除玩家设备。

保留3年复核的最小交易/权益/售后记录与私人资料表级权限或字段去关联；不因保留交易而保留完整剧情。RK1不建立物理外键；归属脱敏方式在字典节点核对，避免删除Player造成必须保留的现金证据级联丢失。
