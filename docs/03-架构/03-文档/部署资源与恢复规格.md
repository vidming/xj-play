### 1.1 同库最小权限边界

以下“身份”表示凭据与操作职责，不是MySQL SQL角色，也不代表已有账号。当前5.7.14不采用8.x的角色或动态权限语法；实际授权清单须随保留的底座模块及游戏迁移逐表核对，不在本阶段生成或执行GRANT。

| 职责身份 | 所需数据访问 | 明确边界与验证要求 |
| --- | --- | --- |
| 平台业务运行 | 经过核准的`xj_`及保留底座表所需SELECT/INSERT/UPDATE/DELETE，逐表按实际操作缩减 | 无DDL、账号管理、转授权、FILE或SUPER；API、任务和通知按当前单应用边界可共享受限身份，不为权限强拆服务 |
| 独立游戏可信服务（确有需要时） | 仅该游戏登记的具体表清单及必要DML；共享表内的主体、环境与作品归属仍由服务端检查 | 不直接读平台会话凭据、现金、订单或权益表，不访问其他游戏表；核身份与权益走平台API；纯前端游戏无需数据库账号 |
| 结构迁移 | 按批准迁移涉及的明确对象和DDL临时授予 | 与日常运行凭据分离；不默认允许DROP、全库管理或转授权；新增表先核清单再授予运行身份，不因前缀匹配自动获得权限 |
| 备份采集 | 按最终工具、客户端版本、备份内容及日志采集方式核最小权限 | 逻辑导出、读取日志、宿主快照的权限不同，不一次性给全局管理权限；不允许恢复覆盖业务数据；备份含敏感资料，单独控制读取 |
| 恢复操作 | 仅获批隔离恢复目标、对象与制品；确需合入时另有审阅范围 | 不由业务进程持有；先隔离旧写端、核删除与撤权覆盖，禁止单游戏整库覆盖；恢复后重新核权限 |
| 只读分析/支持 | 经核准的最小查询、脱敏导出或受限API | 只读不等于可读全部私人字段；避免直接授予平台全表SELECT；分析账号不兼任备份或迁移 |
| 浏览器与静态构建 | 无数据库凭据；通过受控API或公开快照取得许可数据 | 游戏包、管理端脚本、构建产物及sourcemap不得带数据库或备份密钥 |

`xj_`、`xjg_<gameKey>_`是命名登记，不是MySQL表级通配授权。运行身份按明确表清单授权，不能用`xj_play.*`代替游戏前缀隔离；表级授权也不能替代同一表内的对象归属检查。应用所需的特殊语句或工具权限须在相应验证项中证明，不以扩大到全局权限解决报错。

本次MCP只读元数据核查显示，**当前工具账号**可见28类全局且可转授权限；这不代表未来应用账号已经配置，也不授权用工具账号作为运行账号。后续验收须从实际运行身份分别验证允许操作和越界拒绝，留存去身份化结果；不把账号名、来源主机或授权秘密写入项目材料。官方权限语义见[同库核查第9节](../05-资料/同库数据与限制记录核查.md#9-权限与备份的官方语义依据)。

## 2. 游戏与平台在部署上的边界

故事主线互动游戏、线索/链接/仿真网页探索游戏均可拥有独立前端工程。平台提供宿主、游戏版本入口及约定协议，不接管其剧情与页面。

公开包仅含公开引导及可公开试玩内容。受控正文、答案和隐藏资源不能进入公开HTML、脚本、sourcemap、预缓存或离线包。每次受控资源请求由服务端校验当前主体、run、作品版本、发布状态和权益。已发送给浏览器的内容无法通过后续撤权“收回”；撤权控制后续访问，不宣称绝对防复制。

场景、章节、买断映射游戏侧contentKey，授权以购买或有效授予来源计算，不按URL访问或重进收费。宿主向服务端代理公共能力，游戏不获得平台Cookie、长期令牌、支付密钥或任意API代理权。试玩与正式游玩采用明确入口模式及各自资源范围。

## 3. 静态发布与回退

1. 作品/版本发布事务写业务事实与RENDER outbox，携带catalogRevision及明确公开快照引用。
2. 构建从受限公开快照读取资料，产物记录源码、依赖锁定摘要、catalogRevision、文件摘要和兼容协议。
3. 检查公开资料范围、路由、404、资源完整性与目标版本。成功后切换完整制品指针，失败保留旧展示并标明后台构建状态。
4. 私人路由只加载空壳和经认证的动态响应；不预渲染账号、订单、云档、运行凭据或后台预览。不存在的公开作品仍为404。
5. 停售、暂停、撤权和游戏版本禁用由实时服务端拦截，不能等待静态重建。旧公开价格只是展示快照，下单必须重取报价。
6. 应用/静态制品回退使用兼容版本；现金账及已发生业务事实不因回退清零。数据库采用兼容的扩展迁移；不可逆迁移另行提交影响与恢复验证。

## 5. CR1目标的口径

- RPO目标15分钟：故障时刻与最后一个**可验证的业务一致恢复点**之差。数据库、私有对象、可用制品及所需密钥均要覆盖；不能只看数据库备份时间。
- RTO目标4小时：从事后确认的服务中断起点，到完成隔离恢复、限制重放、资金查证和业务开放门禁为止。监控发现延迟包含在内；不能从工程师开始操作才计时。
- 两者均未实测，不是已达到的SLA。没有值守、故障替代资源或兼容制品时，即使数据库支持PITR也无法承诺达标。
- 删除、撤会话、撤权等安全限制须追平故障前已接受的操作；它们不能利用15分钟窗口被静默丢弃。无法证明覆盖时保持隔离。
- 渠道真实现金不受主库回滚支配。支付、退款UNKNOWN及晚到账要从渠道和独立证据查证，不能把恢复点后的款项当作不存在。

## 6. 数据库与对象的一致恢复

候选设计要求：对象先以不可变ID上传，验证长度与摘要后，数据库事务才引用该对象并更新业务revision。上传完成但事务失败的对象可作为孤儿清理；清理必须等待引用检查、上传/重试窗口及备份恢复引用窗口，不能误删仍被备份引用的对象。

数据库每个恢复点关联对象清单，包含objectId、精确版本ID、摘要、编码后未压缩字节数、关联实体/revision和数据类别；同时覆盖上传计划、未决/迟到候选、固定profile及必要密钥引用。恢复按清单核验，不根据“当前同名路径”推断历史内容。对象归档落后时，该数据库点还不是有效业务恢复点。

存档沿用每账号/作品1当前＋1上一恢复点及每份1048576字节规则，不因底层对象版本保留就把更多历史存档暴露给玩家。存档冲突双方保留；游戏本地来源不被恢复流程擅自覆盖。

密钥版本、密钥可恢复性和访问权限属于恢复前提。真实密钥不写入文档/仓库；缺密钥导致对象无法解密的恢复点判为不可用。

### 6.0 数据库备份路线比较与验收条件

下列比较细化已确认CR1，不新增已批准的备份产品或实现方案。推荐先核“一致全量＋连续binlog＋独立故障域备份”的可行条件；当前日志关闭，实际启用、工具选定、保留策略、资源和费用仍未批准。

| 路线 | 可解决的问题 | 局限、成本及本项目位置 |
| --- | --- | --- |
| 一致全量＋连续binlog归档 | 从一致基线沿连续变更恢复，缩小仅靠全量的恢复间隔；可按明确截点核对恢复点 | 需要启用日志及宿主管理条件、容量/归档/断链告警和恢复算力；全量与日志坐标必须准确匹配；是优先核查方向，尚未实现 |
| 宿主/托管快照或产品恢复能力 | 若现有环境已提供，可复用其一致性、日志留存及恢复入口 | 必须核产品实际覆盖、应用一致性、恢复耗时、独立故障域、权限及价格；当前不知是否存在，不新选云厂商 |
| 仅周期逻辑导出/单份快照 | 可作为结构与数据基线、迁移辅助或上述路线的一部分 | 单独不能证明连续恢复、15分钟业务一致点及故障前安全限制尾部；不能代替CR1或作为默认达标方案 |

以`mysqldump --single-transaction`作为**候选逻辑导出语义**时，只把其一致性结论用于事务表，并约束备份期间的并发DDL；不把该选项理解为任意引擎、结构变更或外部对象的全局快照。是否采用此工具及具体参数，要连同客户端版本、所需权限、全量对应的日志文件/坐标和实际导出内容核验；5.7.14的权限条件不能照搬5.7后续补丁或8.x的BACKUP_ADMIN。当前全库无可见表，尚不能断言未来全部底座/游戏表实际均为InnoDB。[官方语义依据](../05-资料/同库数据与限制记录核查.md#9-权限与备份的官方语义依据)。

备份索引记录一致基线、数据库/客户端版本、日志起止及连续性、备份校验摘要、对象清单与制品摘要、必要密钥引用、限制覆盖依据、保留及销毁状态。归档失败、日志缺段、磁盘容量不足和对象/密钥缺失均使对应恢复点无效。加密备份的读取/删除权限与生产写入身份分离；同一宿主另一个目录或同一存储集群另一个桶不能直接当作独立故障域。

即使全量和连续日志完整，也必须另核它们覆盖到的最后提交与故障前最后**已接受限制**的差距。延迟归档的完整前缀仍可能缺尾部，不能从现有最大seq倒推出“没有后续注销/撤权”。本轮未确定新的接受证据设施；可恢复计划或可信接受范围缺失时沿用7.2隔离，不能把备份方向说成限制零遗漏承诺。

后续运行验收至少需要：实际运行身份的越权拒绝；一致导出及DDL窗口；基线与日志衔接和故意缺段检测；对象/密钥/制品完整核验；故障前限制尾部覆盖与缺证隔离；单游戏恢复不改其他游戏/现金；包含隔离、资金查证及开放门禁的总RPO/RTO计时。均未执行，文档检查不算恢复演练。

### 6.1 OSF1的元数据与正文恢复单元

这是已确认产品方向内的恢复设计，FM1已确定filer同库原版mysql/filemeta后端方向；精确制品、角色拓扑、备份工具及资源规格仍待取证。不得把单进程mini启动当作已满足CR1，也不默认引入Kubernetes或三节点集群。固定源码依据及备份默认项限制见[候选对比第3节](../05-资料/对象存储候选对比.md)。

| 恢复单元 | 必须保留与关联的内容 | 核验门禁 |
| --- | --- | --- |
| 平台MySQL | 业务恢复点、对象引用行、业务revision、引用清单及备份编号 | 每个有效引用解析到精确存储配置/版本；主库快照不能证明注销/撤权已追平 |

| 独立备份目录 | 数据库截点、对象清单摘要、filer/volume备份编号、制品摘要、限制日志覆盖引用和密钥版本引用 | 位于满足约定的独立故障域；恢复权限与生产写入身份分离，不随主库一起回滚 |

不以各组件“同一时刻有快照”推定跨组件原子一致。先冻结清单及引用窗口，再取得覆盖其全部有效精确对象版本的元数据和正文副本；允许对象备份包含额外孤儿，但不能漏有效引用。持续写入时必须证明备份捕获/日志追平覆盖清单，不能依赖默认备份参数。全量及增量备份期间，有效清单对象、其旧profile和必要密钥均不能被普通GC提前回收；有可信注销/删除要求的对象按下述排除集合禁止复活。

FM1收口的**待执行验收清单**：固定实际SeaweedFS发行制品、源码提交、依赖/制品摘要与目标系统架构；由已批准迁移预建原版`mysql`后端所需`filemeta`，对照固定源码DDL及MySQL5.7.14核字段、索引和字符集；运行身份只获该显式表所需DML，拒绝运行期建/删表。`filemeta`与`xj_`业务表共享同一次MySQL一致恢复点及日志链，但volume正文、master所需状态、S3鉴权/版本化配置、必要密钥和应用制品分别登记备份编号、来源故障域与摘要。备份目录为每个数据库点登记精确对象版本到filer映射及volume字节的校验结果；不以`filemeta`行数或“volume可启动”代替全量精确GET。制品、角色、连接配额和备份负载尚无实测，4.50只是已读取的源码取证点，未冻结生产制品或批准启动。

恢复先在库外关闭业务写入、隔离旧写者，按第7节核实同库快照后的限制覆盖及必要计划。只有可恢复的完整记录及可信APPLIED删除/消退依据，才形成“不得复活、无需恢复正文”的排除集合；同库旧快照或对象缺失不能自证覆盖。覆盖未知时相关私人/付费恢复保持隔离，不以缺密钥或GET缺失倒推已合法删除。

随后在隔离环境还原所需存储角色、权限和仍有合法用途的密钥，先把隔离/排除集合施加到恢复数据，验证其余必须恢复的有效引用：逐项精确读版本，比较实际上传及解密后的长度/摘要，并验证当前档、上一点及冲突双方。有效引用无版本、摘要不符、缺chunk、权限未知或无法解密都登记为阻塞缺口；不能改读同key最新版本、清空存档或开放缺正文的游戏来宣称恢复成功。已可信消退的对象/密钥不因旧快照仍有引用被要求重新取回。

该恢复点验证完成后，仍须执行第7、8节完整限制追平、未决查证和资金核实。首批全量/增量备份及每次恢复演练应覆盖全部清单项：有效引用核字节，排除项核可信依据；日常抽检只作预警，不能据抽检证明完整恢复。RPO按实际可证明的一致点计算，RTO覆盖上述工作和业务开放门禁。

### 6.2 消退证据与清理状态

主资料7日、备份30日目标不变。`purge_not_before`只是最早可清理下界，保留窗口冲突或能力缺失须登记异常和影响，不能静默延长承诺或伪称达标。私人对象不使用无论目的都永久锁定的保留策略。

| 状态或对象层 | 可证明的事实与下一条件 |
| --- | --- |
| DELETE_PENDING | 持有对象行守卫、核全部消费者及未决操作/备份引用后排定精确清理；后续引用禁止。引用核查与GC不能各自无锁运行 |
| LOGICALLY_DELETED | 精确版本删除结果及查询已查证，受控入口不可再读；删除标记、列表不可见或GET缺失仍不能证明底层字节消退 |
| 所有有效/历史版本及分片 | 按精确版本和删除队列核清单；未完成上传、孤儿及重试落物也在范围；不只删除“当前版本” |
| volume副本与待回收空间 | 覆盖实际全部副本、离线副本重新接入规则及vacuum/回收完成证据；单次DELETE回执或执行过vacuum命令不足以证明全部字节消退 |
| 快照、备份与缓存 | 逐份到期/销毁，或采取经验证且覆盖全部密钥副本的适用处置；同集群另一个桶不是独立备份，备份副本不可无限重建过期私人数据 |
| PURGED | 全部适用层证据齐全、核实时间及责任明确后才设置；若底层介质只能提供逻辑回收保证，须明确该限制并另提目标适配，不能声称取证级物理擦除 |

限制重放记录和可压缩检查点保留到仍可能复活数据的备份窗口结束，不能机械按创建后30日删除。清理证据使用最小不透明编号，不附剧情或通知正文；私人定位元数据同样分类消退。当前未运行删除、vacuum、备份或恢复命令，以上均为后续必须验证的设计条件。

## 7. 同库限制记录、事务与恢复边界

SD2是用户2026-10-26最新明确指示：平台、限制记录及每个独立游戏的所有表和表数据先放在当前MCP连接的`xj_play`，按业务前缀区分。这覆盖此前LR1的独立MySQL限制库方向；不另建限制数据库，不保留两个数据库之间的预备/补写协议。具体当前模型和只读实况见[同库核查](../05-资料/同库数据与限制记录核查.md)。

### 7.1 同一事务提交的内容

| 对象 | 当前职责 |
| --- | --- |
| xj_restriction_gate | 当前环境安全写入门禁与运行代次；整库恢复也会恢复它，不能依赖恢复出的OPEN自行开流量 |
| xj_restriction_operation | 原opId、可信主体/动作/原请求键、最小计划、已提交结果；合并原独立操作镜像 |
| xj_rl_head / xj_rl_event | 受锁保护的连续序号及已提交APPLIED事件；用于现存内容核验，不是独立防回滚证据 |
| xj_rl_checkpoint | 压缩承接必要计划、防重索引及完整原回执；同库快照仍可丢失其后事件 |
| xj_restriction_replay | 本次恢复前缀、可信目标、排除/隔离集合及证据；未知目标可空，缺证不得READY |

服务端先认证并取得稳定请求键，事务按**门禁→限制头→原操作→业务守卫→目标行**的固定锁序进行。核环境、可信数据库身份、OPEN和epoch，再按原主体/动作/请求键查既有操作；同计划已成功重试返回原结果，同键异计划拒绝，不先按已过期的expectedRevision拒绝原成功重试。

首次操作在同一InnoDB连接、同一短事务内完成业务revision校验、限制变更、操作APPLIED、事件/头推进和必要outbox。seq取头锁下`last_seq+1`，与全部效果一起提交。失败显式回滚整个事务，不落独立PREPARED/ABORTED；原`xj_rl_operation`及仅为跨库取消竞争设置的CANCELLED协议移除。MySQL语句失败不自动等于整个事务回滚，入口必须显式终止本次事务。

成功响应只说明对应限制已提交。注销分类清理、游戏侧数据删除、现金退款仍以各自对象状态查询；日志APPLIED不证明这些后续任务完成。outbox用于游戏/对象/通知等提交后的可靠任务，不再承担另一数据库的APPLIED补写。事务内不等待游戏HTTP、支付渠道、邮件或对象存储。

COMMIT响应丢失按原键从当前可信写端查证，保留请求结果未知语义；不能换键重发。同库事务避免了双库中间态，但整库恢复后原操作行缺失仍不足以证明未执行，尤其不能据此重发真实现金动作。恢复期执行7.2的隔离门禁。

同一规则适用于重置口令的旧会话撤销：一次性令牌消费、口令更新、撤会话与限制记录同事务提交。原请求重试通过原动作、原键和可信请求绑定查原结果，不能仅因令牌已消费而丢失原成功结果；限制计划和日志不保存口令、原始令牌或密码哈希。

入口是否直接返回限制完成与实际执行事务分开。免费领取、升级、撤回未最终确认的注销等实际授予/恢复动作同样受门禁和业务守卫控制，单纯授予不伪造撤权事件；支付通知可靠收件仍使用渠道原生确认协议，不表示权益已经处理。查证、售后、退款、任务重试若最终触发撤权，其实际执行事务遵守本节，不在持锁事务中调用渠道，也不以重试受理代替完成。

### 7.2 同库故障与尾部丢失

平台、每个游戏、限制链、检查点、幂等与outbox共享数据库故障和恢复边界。`xj_`与`xjg_<gameKey>_`仅表示归属；不同前缀、不同账户或不同目录不产生独立恢复保证。

自洽的旧快照`1..H`不能证明事故前没有`H+k`。不能用同库最大seq、检查点或恢复出的门禁自证“注销/撤权全部追平”。需要可恢复的全量/连续日志以及能确定故障前最后接受范围的可信证据；只有一个更早锚点仍不足以恢复缺失计划。备份材料放在库外不等于另建应用数据库，也不等于已核实备份可用；本轮未新增服务或批准费用。

当前只读发现`log_bin=OFF`，因此**本实例当前不能提供基于其binlog的PITR链**。现有快照/宿主备份是否存在、覆盖到何时均未验证；`innodb_flush_log_at_trx_commit=1`与`sync_binlog=1`不能替代未启用的binlog或防止整库旧快照回滚。RPO15分钟/RTO4小时继续是待演练目标，当前未满足证明条件，不因合库静默降低标准。

恢复先在库外关闭应用写入口、定时任务及新支付，实际隔离旧主/旧连接，再读取恢复数据；恢复出来的OPEN不能自动打开入口。核实目标头及完整计划/尾部后，才形成删除排除集合并验证其余有效对象；证据不足的私人恢复、付费资源和相关scope保持隔离。公开目录可分范围只读，不表示受影响业务或全平台RTO达标。若将来要求无损继续服务而现有证据不足，需另提资源/恢复方案供用户确认，不自动恢复LR1或启用对象CAS。

#### 7.2.1 故障前接受范围的证据路线（RC1已确认）

2026-10-26实际选择消息确认RC1。这里的“接受”指服务端向调用方确认限制已生效，不把客户端发起请求、异步队列受理或对象上传当成限制已提交。恢复不能只比较快照内的`last_seq`和归档日志的末尾：它们同样可能一起落后于事故前已应答的操作。采用**库外、独立故障域的持久计划见证**，仅存最小限制计划、原请求键、可信作用域、事件摘要与不含敏感正文的定位信息，不增设游戏业务数据库；它是与数据库日志互补的恢复材料，并不替代SD2同库事务。

| 写入时点 | 必须成立的条件 | 崩溃或不可用时的处理 |
| --- | --- | --- |
| 入口与预写 | 所有限制入口和后台/任务实际执行撤权的路径先经统一守卫；在数据库事务之前，以原请求键及计划摘要把可重放的最小计划持久写入独立见证，并取得可核验的落盘回执 | 见证不可用时不执行或确认新的限制；保留请求待查，不能偷偷改走仅同库写入。停写策略及具体产品/资源/费用仍须后续确认，RC1不代替采购或建表 |
| 同库提交 | 在固定锁序内完成限制、操作、APPLIED事件、头、业务守卫及必要outbox的原子提交；同键异计划拒绝 | 预写成功但事务失败/结果未知会留下待核意图，不据预写直接宣称限制完成；按可信写端原键查证，无法查证则隔离该scope |
| 应答与锚定 | 仅在事务已确认提交且预写回执已持久时答复成功；库外追加提交关联或周期封口，记录已应答前沿及数据库日志坐标/摘要 | COMMIT已发生但应答前崩溃仍可能存在“未应答但已提交”；见证与数据库不一致时查证/隔离，不能以库外意图直接改写现金或自动补发权益 |
| 恢复与开放 | 先在故障域外隔离旧写者，取得可验证的见证前沿及其完整计划，再与一致全量、连续日志、同库事件及对象清单核对；对缺失的已应答限制重放或排除，对不确定意图逐scope隔离 | 见证不可读、缺段、身份/摘要不符、日志无法恢复到必要提交，或无可靠事故前应答前沿时不得将相关私人和付费scope标为READY |

**前沿的完备性要求**：所有可返回“成功”的入口必须受同一协议约束；见证的持久回执必须具备明确的顺序、去重、完整性、保留和故障域证明。事故时需能隔离所有旧写端，并确认最后应答边界或保守纳入全部可能已提交意图；不能只拿恢复后的同库头、见证中最后一条记录或墙钟时间推断无遗漏。若库外材料仅为异步镜像，仍可辅助定位和缩小隔离范围，**不能**作为故障前已应答限制零遗漏证明。当前没有见证设施、保存期限、可用性或故障演练证据；RC1只确认架构方向，不授权建立它，也不宣称RPO/RTO达标。

RC2与RC3为未选项，不再实施。若生产前资源、预算或故障域不支持RC1，须提交可核实的局部开放范围、未达CR1目标的影响及重新取舍，不能静默降低标准或改写成RC2。

### 7.3 平台与每个独立游戏的同库归属

平台保留`xj_`表族，内部按目录、交易、运行、存档、运营、限制等领域划分；已有底座固定前缀按源码保留；FM1明确SeaweedFS内部表`filemeta`作为例外，仍在`xj_play`，不计入平台48表，运行身份仅按该显式表授权；本轮未建表或授权。每个游戏登记不可复用的`xjg_<gameKey>_`前缀，如G-A用`xjg_ga_`、G-B用`xjg_gb_`作为说明，当前没有创建这些游戏表。完整剧情、线索、角色及游戏专有数据由各自工程设计到对应前缀，平台不为收费解析统一剧情树。

`gameKey`限制为小写字母开头的字母数字、最长16位；前缀由服务端登记并写入`xj_game.data_namespace`，登记后不可复用。具体表名清单由受控迁移定义，总长度不超过MySQL标识上限；HTTP参数、contentKey或网页链接不得拼接成SQL标识。前缀是归属约定，权限仍按具体表授权，不使用“前缀通配GRANT”冒充隔离。

独立游戏前端不直连MySQL、不持数据库凭据。纯前端游戏可通过平台SDK/API使用通用身份、权益、存档和事件，不强制每个游戏新增后端；需要专有持久逻辑时由可信游戏后端持本游戏表的最小权限，通过平台API核身份/范围及付费权益，不读取平台会话凭据表或直写订单、现金、授予与限制表。同库也不授权其他游戏读写本游戏数据。

同一Java应用内已纳入平台的短业务事务可用一个连接；单独游戏服务经HTTP调用平台仍是两个提交边界，不能因底层同库就宣称自动原子。跨服务动作使用原业务ID、幂等、outbox/回执和查证，不在持锁事务内等待另一个服务；游戏结果不能变成可信付款或解锁依据。游戏账号关联使用平台核验的作品域身份与归属映射，不让客户端自报playerId获得权限。

RK1明确全部表关系仅作逻辑关联，不建立数据库外键或ON DELETE/UPDATE级联约束。写入服务在同一事务核目标存在、当前游戏/主体/环境归属及可用状态；关联写入与删除共用业务守卫和固定锁序，避免“先查存在、随后目标被删”的竞争。必要主键、唯一键与查询索引保留；导入、修复、后台批处理执行同等校验，孤儿/错域巡检先隔离核实，不自动补权益、删现金或把物理删除当作清理完成。

注销/删除清单覆盖`xj_`及所有关联`xjg_`前缀的私人数据；平台保留受控最小清理范围和游戏适配器回执，失败按scope隔离及复核，不把一个游戏删除成功当整个平台完成。单游戏更新/回退只操作该前缀迁移及兼容数据，禁止直接整库还原影响其他游戏、现金或权益。单游戏数据恢复先在隔离暂存区核当前身份、删除覆盖、范围及存档revision，再受控合入；不创建已获批准的新正式业务库。

### 7.4 确定编码、回执与压缩

沿用项目内部确定编码v1，作为平台后端协议而非游戏公开API。null=`N`，true/false=`T/F`；字符串=`S + u32be(UTF-8字节数) + 原字节`；数组=`A + u32be(元素数) + 逐元素编码`；对象=`O + u32be(键数) + 按UTF-8键原字节排序后的键值编码`。拒绝重复键、非法UTF-8、未定义类型及隐式Unicode归一化；整数使用无前导零的规范十进制字符串，不能经JavaScript浮点数。

计划摘要为`SHA-256("XJLR/PLAN/1" || encode(planEnvelope))`，绑定可信initiatorRef/requestKey/action/scope/expectedRevision/planSchema/minimalPlan，不含重试变化的时间、epoch和新随机opId。genesis为`SHA-256("XJLR/GENESIS/1" || authorityUuid16)`；事件摘要为`SHA-256("XJLR/EVENT/1" || authorityUuid16 || u64be(seq) || u64be(epoch) || previousDigest32 || u32be(recordBytes) || canonicalRecord)`。APPLIED的canonicalRecord含完整最小计划、原操作及结果；数据库索引列与原确定字节逐项一致。

原回执保留authorityRef/epoch/seq/opId/phase/planDigest/eventDigest。检查点摘要为`SHA-256("XJLR/CHECKPOINT/1" || authorityUuid16 || u64be(throughSeq) || throughDigest32 || u32be(stateBytes) || canonicalState)`。检查点在固定一致前缀下承接有效限制、未决清理、必要防重映射及完整原回执，核可靠恢复副本后在头锁下切同head指针，再清覆盖前缀。被事件引用的操作不能删除；下一检查点继续承接仍必要的回执，不能用当前epoch重造旧回执。

当前`max_allowed_packet=4194304`，MEDIUMBLOB类型上限不是实际可传额度；计划/事件/快照和协议封装均须在写前核可配置安全额度，并低于连接/服务器包长限制，不能把多MiB快照硬塞或截断。超限停止压缩、保留唯一事件载体并登记容量风险，不擅自提高配置。完整链/检查点哈希只能发现现存内容不一致，不能证明没有整链回滚或尾部丢失。

### 7.5 版本、环境与执行范围

当前目标为MCP所连`xj_play`／MySQL5.7.14。原8.4研究只保留为历史比较，不能证明本版本语法、驱动、权限或性能。模型采用InnoDB、显式utf8mb4/ASCII精确标识；RK1全部关联只表达语义，不建立物理外键，存在/归属/删除并发由应用服务与事务守卫负责；不依赖被忽略的CHECK、SKIP LOCKED、8.0专有SQL或0900排序规则。BOM管理的Connector/J9.7.0官方支持MySQL8.0+，不覆盖当前5.7.14；现有Java17／Boot／MyBatis的有效依赖与适配候选尚未运行验证，具体见版本核查6.1；不自动切换驱动或升级服务端。

SD2初核执行3条只读MCP元数据查询；本次权限与恢复补查另执行3条：当前库/版本/可见表计数、白名单变量、仅汇总作用域/权限种类/可转授的当前工具权限。两组结果在[同库核查第2节](../05-资料/同库数据与限制记录核查.md#2-当前mysql-mcp实况)区分记录，不把当前工具的全局管理权限当成应用所需权限。无业务行读取，无DDL/DML、迁移、用户/授权变更、binlog开关或重启。保护配置不读不改。当前连接不代表正式生产环境已经批准；本地/验收/生产隔离与资源条件仍待完整架构验收，不把同一正式库的不同前缀包装成环境隔离。

## 8. 恢复顺序与开放门禁

| 顺序 | 操作要求 | 通过证据/失败处理 |
| --- | --- | --- |
| 1 隔离 | 停止写入、定时任务及新支付入口；保留必要通知收件证据；记录事故时间与影响范围 | 若通知收件设施也不可用，恢复后主动查渠道，不假称已收 |
| 2 选点与限制预核 | 核实同库快照后的限制覆盖、最后接受范围及可恢复计划，形成可信删除排除/未决隔离集合；校验全量/增量链、数据库版本、有效对象、密钥及制品兼容 | 无限制覆盖证明保持隔离；仅有可信删除依据才排除旧引用，不以对象缺失倒推删除 |
| 3 恢复 | 在隔离环境恢复主库及兼容应用，先施加排除/隔离集合，再验证其余有效对象；未决上传单独核查，任务保持暂停 | 不复活已删除对象，不把合法消退当普通缺正文；不覆盖线上现金事实，不立即发权或退款 |
| 4 限制追平 | 重放注销、撤会话、撤权、清理及暂停范围；核对记录高水位 | 缺覆盖保持限制，不能复活已注销账号 |
| 5 现金查证 | 按商户/渠道作用域核未决付款、关单、退款、晚到账与渠道账单 | 每笔真实收款单独记账；重复付款不重复发权，按规则逐笔核退 |
| 6 权益重建 | 按订单、grant、upgrade等来源重算，核净实付抵扣与售后approved_plan | 不以“有订单”推定已付，不以已付推定仍有权益 |
| 7 功能与权限 | 核三类contentKey、试玩、正式运行、私有资源、存档CAS、管理员对象权限 | 关键门禁未过，相关业务继续关闭 |
| 8 开放 | 记录负责人、证据、开放范围和剩余风险；重新建立监控及备份 | 分范围开放不表示整个平台RTO达标；未满足整体边界仍记目标未达到 |

支付未知期间不能无提示重开同一订单的另一渠道支付；先查旧尝试并按渠道规则关单。退款受理、到账和撤权分别核实。恢复不自动触发真实退款或其他现金操作。

## 9. 后续演练场景与验收证据

以下属于架构定义的验证要求，不是本轮执行记录，也不提前编排阶段4工期：

- 主库故障或误删，含不连续增量日志；记录最后业务一致恢复点和总RTO。
- 对象上传后事务失败、主库恢复点比对象备份新、对象摘要不符或缺密钥；确保不会带缺失付费内容开放。
- 同库限制事务提交前/后崩溃或提交响应丢失；核业务/操作/事件/outbox全有或全无及原键重试；旧快照尾部缺失须保持隔离。
- 在途付款/退款跨故障点、晚通知和重复收款；现金不丢、不重发权、不以UNKNOWN误退款。
- 暂停游戏、旧静态详情、旧会话及旧run跨恢复；实时门禁持续有效。
- 存档同一revision冲突、当前/上一点恢复、个人删除以及备份到期；不增加玩家可见历史数量。

证据至少包括事故起止、数据库恢复点与日志连续性、对象及制品摘要、限制记录高水位、渠道查证水位、逐门禁结果和资源账单。失败须说明范围、风险及调整方案，重新提交影响，不能把15分钟/4小时写成已经满足。
